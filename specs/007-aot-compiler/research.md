# AOT compiler: research dossier

## execution-model: Action and operation execution model (Action/EndableAction/TimelineAction, operation chain, scope, control flow, error behaviour)

An action is an array of IResolvedOperation {id, systemName, operationData (deep-copied from config at resolve time), instance} (configuration/types.ts:514-519; configuration-resolver.ts:557-561). Action._runOperations (action.ts:61-88) creates a FRESH scope stack per run, containing one root scope {currentIndex:-1, eventbus, operations} (action.ts:90-100), and calls executeOperation (action.ts:140-246), a synchronous while(true) loop that only leaves the loop when an operation returns a promise (then it resumes with a recursive executeOperation call from .then, sharing the same scopeStack, action.ts:212-235) or when index >= operations.length (resolve(operationData), action.ts:164-167). There is no per-operation try/catch: one try/catch wraps the loop and rejects the run promise with the error annotated with operationSystemName/operationIndex (action.ts:239-245, 265-277).

Per step the loop does, in this exact order: (1) take the TOP scope of the stack; if scope.newIndex!==undefined, index=newIndex and delete it (157-160); (2) scope.currentIndex=index (162); (3) if index>=length, resolve with current operationData (164); (4) fetch the op; build configuredData = (loop-iteration ? cached forEach data : copyConfiguredOperationData(op.operationData)) (172-180); (5) mergedOperationData = Object.assign(operationData, configuredData) i.e. the PREVIOUS operation's output object is MUTATED in place and configured keys override same-named incoming keys (181-184); (6) if systemName is when, push a child scope; if forEach and not an iteration of the current loop, push a child scope with owner=op and cache configuredData in a WeakMap (186-195); (7) call op.instance.call(scope, merged) with `this` = the (possibly new) top scope (197-200); (8) if the op is endWhen, or endForEach with scope.newIndex===undefined AFTER the call, pop the scope stack (202-208); (9) index++ (210); (10) promise result: wait, then continue with the resolved value as the next input; sync result: operationData = result ?? {} (237). The chain is therefore data-flow: output of op N is (mutated and) fed to N+1, with the configured data of N+1 merged on top.

Start vs end of an EndableAction are two independent runs over two operation arrays with separate scope stacks, separate scope objects, separate scope.variables, and separate operation data. end() gets only what the caller passes (the engine passes nothing, so end ops begin with {}) (endable-action.ts:26-32; eligius-engine.ts uses action[phase]() with no args at 1502, and init actions action.start() at 947). TimelineAction adds an active flag toggled synchronously, a serialising queue so one action's start and end operations never interleave, and idempotence (second start/end is a no-op returning Promise.resolve({})) (timeline-action.ts:54-135). The engine (not the action) decides when to call them, by position range dispatch, reconcile on seek, ends-before-starts, with errors routed to the engine 'error' event (eligius-engine.ts:1502-1527, 1620-1830). Event actions are plain Action instances started with {eventArgs} (actionregistry-eventbus-listener.ts:50).

### Findings

#### Initial operation data and what flows between operations

executeOperation default param previousOperationData={} and `previousOperationData ?? {}` (action.ts:145,149). Timeline actions and init actions are started with NO argument, so the first op receives a fresh {} (eligius-engine.ts:947, 1502 `action[phase]()`). Event actions get a fresh `{eventArgs: [...args]}` per action (actionregistry-eventbus-listener.ts:48-50; the args array is shallow-copied, elements shared). startAction/endAction pass a new merged object (see below). EndableAction.end with zero end operations short-circuits: resolves `initOperationData ?? {}` and creates no scope (endable-action.ts:27-29). Start with zero operations resolves immediately with initOperationData (index>=length at first step, action.ts:164).

**Static or dynamic:** Static: the initial shape is known per trigger kind (timeline/init: {}, event: {eventArgs}, startAction: caller data merge). Contents of eventArgs are dynamic.

#### Mutation vs copy of operation data (the central data-flow rule)

Object.assign(operationData, configuredData) mutates the object returned by the previous op (action.ts:181-184). Operations typically mutate and return the same object (removeProperties does `delete` in place: remove-operation-properties.ts:30-35; when.ts:95; setStyle.ts:78; selectElement.ts:128-156) so a single object identity usually flows through the whole chain. Some ops return NEW objects: wait (rest-destructure, wait.ts:22-27), startAction/endAction (rest spread, start-action.ts:32-36, end-action.ts:32), setOperationData (rest + spread, set-operation-data.ts:27-42; override:true returns only resolved properties and drops everything else), invokeObjectMethod (newOperationData), customFunction when async (internalResolve(resolve,{},operationData) = {...{}, ...operationData}, custom-function.ts:65-69, helper/internal-resolve.ts:4-14). Sync return value `undefined`/`null` is replaced by a new {} (action.ts:237), so data is silently dropped; a resolved promise value of undefined/null likewise becomes {} (action.ts:145,149). Aliasing consequence: any value stored in operationData by reference (jQuery selection, arrays) is shared with later ops, global store copies, etc.; only the container object is reused.

**Static or dynamic:** Partially static. Which key set exists after each op is mostly statically known (the @erased/@dependency/@output metadata describes it) except where keys come from runtime data (setData to $operationdata.x, customFunction, loadJson, invokeObjectMethod methodResult). A compiler can turn operationData into local variables only if it proves no op observes object identity or enumerates keys (several ops do: addControllerToElement passes the whole operationData to controller.init(operationData), add-controller-to-element.ts:54; startAction merges all keys into the callee; setOperationData spreads all keys).

#### Configured data merge: copy semantics and proto guard

copyConfiguredOperationData (action.ts:344-363): undefined/empty -> shared frozen {} (279); runs assertNoProtoKeys once per configured object (WeakSet cache, 286-330; throws `<systemName>: operation data must not contain a '__proto__' key (found at '<path>')`); if ANY own value is a non-null object (arrays, plain objects, class instances, jQuery, DOM nodes alike) the whole thing is deepCopy'd on EVERY execution (359); otherwise the configured object itself is returned and only its top-level props are copied by Object.assign (so it is never mutated). deepCopy (operation/helper/deep-copy.ts:34-137): arrays/plain objects recursive with cycle preservation (__proto__ safe via defineProperty), Date/RegExp/Map/Set/Error/ArrayBuffer/typed arrays via structuredClone, functions/jQuery/DOM Nodes/class instances kept by reference. Config is already deepCopy'd once at resolve time (configuration-resolver.ts:559). Note the check `typeof value==='object'` means function-valued entries do not trigger copying. Consequence a compiler must keep: each execution sees a fresh copy of nested configured arrays/objects, so ops that mutate nested config data (push to array, etc.) do not leak into the next run. For a compiler this means literals must be re-created per execution (e.g. object literal / array literal in the generated code, not hoisted constants) unless provably unmutated.

**Static or dynamic:** Static: configured data is known at compile time; the proto-key check can be done at compile time. Copy-per-execution must be reproduced at runtime (fresh literal), or hoisted only when no op can mutate the nested value.

#### Synchronous vs promise chaining and timing

Sync ops run in a loop with no stack growth (action.ts:133-139, 155). `isPromise(result)` (any thenable, util/guards/is-promise) triggers: nextIndex=index (already incremented), `.then(value=>executeOperation(ops,nextIndex,resolve,reject,value,scopeStack), error=>reject(withOperationContext(error,op,index-1))).catch(reject)` and return (212-235). The continuation is a microtask, so code after an async op never runs in the same tick; sync ops before the first async op run synchronously inside start()/end() (the Promise executor runs executeOperation immediately, action.ts:68-87). The resumed call starts with failingOperation undefined and re-fetches scopeStack top, so loops/whens that straddle an await keep their scope. A thenable that resolves to undefined continues with {}. Promise-returning ops in the codebase: addControllerToElement (when controller.attach returns a promise, add-controller-to-element.ts:60-71), animate, animateWithClass, customFunction (only if function returns a real thenable, custom-function.ts:64-70), httpDelete/httpPost/httpPut, invokeObjectMethod (when method returns a promise, invoke-object-method.ts:111-115), loadJson, wait, startAction, endAction. Whether a given op awaits can depend on runtime values (customFunction, invokeObjectMethod, addControllerToElement), so a compiler cannot statically know sync-vs-async for those; generated code must `await` conditionally (e.g. `r = op(); if (isPromise(r)) r = await r;`) or make the whole action async if it must preserve the exact 'runs synchronously until first real promise' timing. TimelineAction relies on that sync timing: finish() is called synchronously via onSettled when ops complete synchronously, so a start and end called back to back both run in the same call stack (timeline-action.ts:92-122, action.ts:54-59,72-87).

**Static or dynamic:** Mixed. Ops that always return promises are static. Conditional-promise ops are dynamic. Exact microtask ordering is only observable by other actions racing on the same elements/eventbus but must be preserved for TimelineAction sequencing.

#### Scope object construction and which fields change per step

Root scope literal {currentIndex:-1, eventbus, operations} (action.ts:93-99); `operations` is the array being run (start OR end ops), so `$scope`-visible state is per run. Per step, only the TOP scope gets currentIndex written (162). Child scopes pushed by _pushScope (110-131) define accessor properties currentIndex/eventbus/operations that read AND write through to the parent (writes to currentIndex propagate to the root), plus `parent`. All other fields are plain own properties of the scope they were set on: newIndex, loopIndex, loopLength, loopStartIndex, loopEndIndex, currentItem, whenEvaluation, owner, variables. `scope.newIndex` is consumed (deleted) at the top of the next iteration from whichever scope is TOP (157-160). Child scopes created for `when` have no owner; for `forEach` owner=the forEach IResolvedOperation (193). Stack is popped only by executing endWhen (always) or endForEach (when it did not set newIndex) (202-208): pops are positional, not matched by identity, so a stray/unbalanced endWhen/endForEach pops the root scope and the next iteration throws TypeError (scope undefined) which is converted to a rejection. A malformed config with missing endWhen/endForEach leaves scopes pushed until the run ends (harmless as the stack is per run). A thrown error leaves the stack as-is and the run is abandoned.

**Static or dynamic:** Static: scope nesting depth and which scope each op runs in are determined by the structural nesting of when/forEach (assuming balanced). Dynamic: the field VALUES. A compiler can map scopes to lexical blocks/locals, but must keep a real scope-like object (or equivalent) wherever customFunction, setData '$scope.…', or `$scope.` chains with runtime-computed paths are used.

#### Property chain resolution against operationData / globals / scope

resolveExternalPropertyChain (helper/resolve-external-property-chain.ts:23-61): null/undefined input -> null (36-38); only strings starting (case-insensitively) with `$operationdata.`, `$globaldata.` or `$scope.` are chains (132-141), anything else returned as-is (including non-chain strings). Segments are checked against __proto__/prototype/constructor (assert-safe-property-chain.ts:154-196) with the CURRENT operation name taken from scope.operations[scope.currentIndex].systemName for the error message (assert-safe-property-chain.ts:201-205) so error messages depend on scope.currentIndex. getPropertyChainValue (get-property-chain-value.ts:34-87): bracket indices `[n]` rewritten to `.n`; throws if an intermediate is null/undefined ('<op>: property chain ... cannot be resolved: ... is undefined'); throws if any step or the result is the global object (window); optional `+suffix` on the LAST segment appends a string suffix (`${result}${suffix}`). `$globaldata` returns a deepCopy of the global value (resolve-external-property-chain.ts:52-54), so mutation never reaches the store. `$scope` chains are resolved against the nearest scope (current then ancestors via .parent) for which `head in scope` is true, falling back to the current scope (81-115); this is why `$scope.variables`, `$scope.currentItem`, `$scope.loopIndex` work from inside nested when blocks, and why properties deleted from the loop scope become invisible. Note `head in scope` also finds accessor props currentIndex/eventbus/operations on every child scope.

**Static or dynamic:** Chain syntax and forbidden segments are statically checkable. Prefix, segments, and the `+suffix` are static; resolution is dynamic (H3). `$scope.<head>` can in principle be resolved statically to a scope level only for names a compiler can prove (variables is always the root's; currentItem/loopIndex belong to the innermost enclosing forEach), but 'declared at runtime' semantic (`in` test) means a property deleted by break/endForEach may fall through to an outer scope.

#### when / otherwise / endWhen exact semantics

when (when.ts:88-104): parseExpression each execution (no cache seen), evaluateExpression against the MERGED operationData (so the `expression` key is in it) and the pushed child scope, removeProperties(operationData,'expression'), this.whenEvaluation=evaluation (own prop of the NEW child scope), if false this.newIndex=findNextFlowControlIndex (nearest depth-0 `otherwise` or `endWhen` after currentIndex, skipping nested when..endWhen pairs; operations.length if none, when.ts:110-127). Returns the same operationData. So: false -> jump TO the otherwise/endWhen op itself (it executes); true -> fall through. otherwise (otherwise.ts:10-34): `if (this.whenEvaluation)` jump to matching endWhen (via findMatchingOperationIndex with self 'when', matching 'endWhen'; operations.length if none); when evaluation was false it does nothing so the else body runs. whenEvaluation is read from the TOP scope only (own property), no parent walk, so otherwise outside a when sees undefined (treated false). endWhen (end-when.ts:9-15): delete this.whenEvaluation; continuePendingLoopJump(this); then Action pops the when scope (action.ts:202-208). All three also get their own configured data merged in (normally empty). Expression grammar/evaluation (parse-expression.ts:290-340, parse-operand.ts): literals 'str', numbers, true/false/null, chains; `==`/`!=` are strict (===/!==), `<,<=,>,>=` JS ordering, no chaining; `!` binds tighter than comparison; `&&`,`||` short-circuit, results of !,&&,|| are boolean, final result Boolean(); a bare operand is truthiness ('false' and '0' strings are TRUE). Operands that do not parse throw at runtime (first evaluation), not at resolve time. Short-circuit means unresolved chains on the unevaluated side never throw. If-without-endWhen: false jumps to operations.length which ends the run. Else-if chains are expressed as nested when inside otherwise and each needs its own endWhen.

**Static or dynamic:** Jump targets (otherwise/endWhen indices) are fully static, so when/otherwise/endWhen compile to if/else. The expression can be pre-parsed and compiled to a JS expression at compile time, but each chain read must keep the same throw-on-null-intermediate behaviour and left-to-right short-circuit order. Evaluation value is dynamic. Exactly one gotcha: whenEvaluation lives on the scope so customFunction/$scope.whenEvaluation can observe it.

#### forEach / endForEach / breakForEach / continueForEach exact semantics

forEach (for-each.ts:36-71): executes in a pushed child scope (action.ts:188-195). First iteration is identified by `this.loopIndex === undefined` on that own scope. It resolves `collection` ONCE: string -> resolveExternalPropertyChain (a non-chain string passes through as the string and then throws 'Expected resolved collection property to be array type...' since not array, for-each.ts:88-112); array literal as is; null/undefined -> treated as empty; non-array object throws. loopEndIndex = matching endForEach index (nested-aware via findMatchingOperationIndex with self 'forEach', for-each.ts:114-129; operations.length if missing). If length>0: loopIndex=0, loopLength=length-1 (LAST INDEX, not length), loopStartIndex=currentIndex (index of the forEach), snapshot = collection.slice() stored in module WeakMap keyed by scope (51-53). Else: newIndex=loopEndIndex and loopIndex/loopLength/loopStartIndex/loopEndIndex deleted, snapshot deleted. Every iteration (including first): this.currentItem = snapshot[loopIndex] (65-68). Snapshot is shallow: item objects are shared with the source, only the array is copied. endForEach (end-for-each.ts:9-25): if loopIndex<loopLength: loopIndex++, newIndex=loopStartIndex (jump back to the forEach op, which re-executes), delete currentItem; else clearLoopCollection. After it, Action pops the scope iff newIndex undefined (action.ts:202-208). Each loop iteration re-executes the forEach operation itself: Action detects it via `systemName===forEach && scope.owner===op` and re-merges the CACHED configured data object (the same object each iteration, not a fresh deep copy; action.ts:172-180,194) into operationData via Object.assign, so `collection` key is re-added to operationData each iteration, and forEach returns operationData that still contains `collection` (forEach has no @erased and never deletes it), i.e. `collection` stays in operationData during and after the loop. Data flows across iterations: operationData carries over from the end of iteration k to the start of k+1 (same object), so a loop body that accumulates in operationData keeps accumulating. breakForEach/continueForEach (break-for-each.ts, continue-for-each.ts, helper/loop-jump.ts): requestLoopJump finds the nearest scope with loopIndex!==undefined && loopLength!==undefined (walking .parent) (loop-jump.ts:29-41,103-116); outside a loop it is a no-op. If running directly in the loop scope: loopScope.newIndex=loopEndIndex (the endForEach), delete currentItem; break additionally clears the snapshot and deletes loopIndex/loopLength/loopStartIndex/loopEndIndex (so the following endForEach sees loopIndex undefined and just pops) (90-101). continue leaves counters so endForEach advances. If inside when blocks: each when pushed a scope and only endWhen pops it, so the jump goes to the enclosing endWhen first (findEnclosingEndWhenIndex scanning from currentIndex+1 at depth 0; pendingLoopJumps WeakMap on that when-scope, loop-jump.ts:71-88,122-137); endWhen then calls continuePendingLoopJump which forwards to the parent (loop scope -> applyLoopJump; another when -> repeat) (48-69). Malformed when without endWhen: jumps straight to loop end from the current scope (78-84). Consequence: break/continue inside nested when execute the REST of nothing but they still run each enclosing otherwise/endWhen path: after jump to the endWhen index, that endWhen executes (cleans whenEvaluation) and continues to the next jump; but note the jump target is the endWhen itself, so code between (e.g. an `otherwise` branch) is skipped. A continue on the last iteration: endForEach sees loopIndex==loopLength and finishes the loop. Edge: loop with a `break` in the first iteration when also nested in a parent loop does not affect the parent (own scope).

**Static or dynamic:** Loop structure (forEach/endForEach pairing, break/continue targets, nesting through when) is fully static and compiles to for/continue/break with labels. Collection and length are dynamic (H3). Must reproduce: collection resolved once and sliced; currentItem is a scope field readable via `$scope.currentItem` chains and customFunction `this.currentItem`; loopIndex/loopLength (last index!) readable via `$scope.loopIndex`/`$scope.loopLength`; `collection` remains in operationData; configured forEach data is re-merged each iteration (so edits to operationData.collection inside the body are overwritten each iteration); empty/null collection skips body but still runs endForEach.

#### Jumps via newIndex are open-ended (user-writable goto)

newIndex is just a scope property consumed at the top of the next iteration from the TOP scope (action.ts:157-160). Any op or host function can set it: setData with target `$scope.newIndex` (documented example set-data.ts:34-37; empty path writes to the current scope, set-data.ts:259-262), and customFunction via `this.newIndex` (custom-function.ts:28-31; the scope view proxy has no set trap so assignment lands on the real scope, 84-105). Any index including backwards or beyond length is honoured (>=length ends the run, action.ts:164). This is an arbitrary goto into the flat operation array, including into the middle of when/forEach blocks, which would then run with the wrong scope stack. A set newIndex on a child scope that is then popped before consumption is lost (e.g. set inside endWhen: it is applied to the scope being popped; but loop-jump deliberately sets it on the parent).

**Static or dynamic:** Static detection is possible: a compiler can scan for setData keys equal to `$scope.newIndex` (any case of prefix) and for customFunction use, and either reject, or fall back to an interpreter/switch-in-a-loop (state machine over op indices) for those actions. Targets given as constants are statically analysable; runtime-computed targets are not.

**Static or dynamic:** Static per operation: the table of scope reads is fixed per op. Which `$scope` fields an op instance reads is statically visible in the configured data strings (except computed ones like customFunction bodies, which are opaque).

#### Resolution order of config value chains and what is resolved when

Only the ops that call a resolver resolve chains, and only the properties they choose: createElement resolves just elementName/attributes/text (create-element.ts:63-72); setStyle resolves `properties`; setOperationData resolves `properties` against the data WITHOUT the override/properties keys (set-operation-data.ts:27-33); selectElement resolves only `selector` (and WRITES the resolved selector back into operationData before destructuring, select-element.ts:128-136); forEach resolves `collection` only when it is a string chain; when parses `expression`. There is NO global pre-pass: other operationData strings that look like chains are passed through literally. resolvePropertyValues (helper/resolve-property-values.ts:171-192) deep-copies a separate `properties` object first, then resolves chains in top-level values and recursively inside plain objects/arrays with copy-on-write; class instances/jQuery/DOM are never walked; when newProperties===operationData it replaces top-level keys in place. Chain resolution is left-to-right in key order (Object.keys order), and a throwing chain aborts the op before any later key is resolved.

**Static or dynamic:** Which properties are chain-resolved per op is static (per-op knowledge needed in the compiler: it must know that selectElement.selector is resolved but e.g. addClass.className is not). Values are dynamic.

#### startAction / endAction / requestAction (action-to-action calls)

requestAction (request-action.ts:33-47): removeProperties(systemName), then operationData.actionInstance = requestNamedEntry(this.eventbus,'request-action', ...) which does an eventbus request answered by EngineFactory._registerResponders -> _findLiveAction(name), throwing for unknown names with a did-you-mean (engine-factory.ts:155-197). Resolution is by name at RUN time against the currently live engine's action lookups (_actionLookups, newest first), so action identity is dynamic (multiple engines/timelines). startAction (start-action.ts:31-53): destructures {actionInstance, actionOperationData={}, ...caller}; returns a new Promise; rejects 'startAction: actionInstance is required' if falsy; calls actionInstance.start(mergeOperationData(caller, actionOperationData)) where mergeOperationData = {...caller, ...actionOperationData} (merge-operation-data.ts:3-8); callee's operation data is a NEW object so the callee's mutations never reach the caller; on success the caller continues with {...caller, actionInstance} (callee's resulting data is discarded); errors propagate by rejecting (annotated by the callee with its own failing op first; the caller's withOperationContext does NOT overwrite an existing operationSystemName, action.ts:272-275). endAction (end-action.ts:31-52): same shape, no actionInstance re-add needed (it is inside caller), continues with {...caller} (includes actionInstance), calls actionInstance.end(merged). The callee has its own scope stack, so `$scope.variables`, loop state, newIndex are NOT shared with the caller. Both always return a promise, so the caller always yields to a microtask even when the callee is fully synchronous. If the target is a TimelineAction that is already active, start resolves immediately with {} without running ops; if its ops are still running, the call waits in the action's queue (timeline-action.ts:54-61, 81-90) - a self- or cyclic-start could deadlock (not guarded).

**Static or dynamic:** Dynamic by name (registry lookup via eventbus at runtime). A compiler can resolve names to direct references when the action set is closed (static presentation), but must handle: actions defined in other configs/engines, the 'unknown name' error timing (at the requestAction op, not at compile time unless the compiler chooses to fail early), and TimelineAction active/queue semantics (must still go through the runtime action object or replicate _active/_sequence).

#### What happens when an operation throws or rejects

Sync throw: caught by the single try/catch around the loop (action.ts:239-245) -> reject(withOperationContext(error, failingOperation, failingIndex)). Non-Error throwables are wrapped in `new Error(String(error),{cause:error})` (271). Annotation sets operationSystemName and operationIndex only if undefined (272-275), mutating the original Error object. Promise rejection: the rejection handler annotates with the op that returned the promise (index-1 captured as asyncIndex, 230-232). Errors thrown while running subsequent sync ops in the continuation are annotated by that continuation's executeOperation call. There is no recovery: the run stops at the failing op; remaining ops (including cleanup ops such as endWhen pops, removeElement, removeControllerFromElement) do not run, side effects already applied (DOM, controllers, globals, eventbus broadcasts) are not rolled back, and operationData is discarded. The failure surfaces as rejection of start()/end(). The Action itself does NOT log (action.ts:35-45). TimelineAction: onSettled -> finish() runs on both resolve and reject so the queue continues (action.ts:61-88, timeline-action.ts:97-122). `_active` is NOT rolled back on a failed start, so a later end() still runs end operations after a partially failed start (timeline-action.ts:59-60,77). Engine: _runActionMethod swallows rejections of timeline-driven start/end into an `error` event of type EngineActionError (action id/name, phase 'start'|'end', cause) and console.error if nobody subscribes (eligius-engine.ts:1497-1527); engine ticks continue. init actions: `await action.start()` in init() so a failing init action rejects init() (eligius-engine.ts:946-948). Event actions: handleEvent uses Promise.allSettled and rethrows (single error or AggregateError) to the eventbus which reports via onHandlerError (actionregistry-eventbus-listener.ts:48-69). Operation failure messages usually name the op and data: e.g. 'selectElement: selector is either empty...' (select-element.ts:138-140), 'startAction: actionInstance is required' (start-action.ts:40), property-chain errors name the op via scope.operations[currentIndex] (assert-safe-property-chain.ts:201-205, get-property-chain-value.ts:62-67).

**Static or dynamic:** Dynamic. Compiled code must (a) reject with an Error carrying operationSystemName/operationIndex (engine reads these to name the failing operation, action.ts:249-258), (b) not catch inside the action body, (c) let TimelineAction-like active/queue bookkeeping continue on rejection.

#### TimelineAction start/end sequencing, activity and idempotence

start(): if _active returns Promise.resolve({}); else _active=true synchronously and _sequence(() => super.start(init)). end(): if !_active returns Promise.resolve({}); else _active=false then _sequence(super.end). _sequence: if not _running, _execute now; else queue a closure in _waiting (FIFO) that runs _execute later and forwards the result (timeline-action.ts:81-90). _execute sets _running=true, stores a finish callback in _finishPending, calls run(); _runOperations (overridden) captures that finish and passes it as onSettled, so it is invoked synchronously inside the Promise resolve/reject wrappers (action.ts:61-88, timeline-action.ts:124-135). If run() performed no operations (end with no endOperations returns Promise.resolve directly and never calls _runOperations) the pending finish is invoked right away (timeline-action.ts:116-120). finish pops the next waiter synchronously (105). Consequence: ops of one action never interleave across a start and an end, a start immediately followed by an end always runs end ops after start ops complete (including async ones), and the active flag flips immediately regardless. An engine tick can therefore call end() while start ops are still awaiting (e.g. wait/animate), and the end ops will run only after the start chain has settled.

**Static or dynamic:** Runtime-only protocol; static aspects: actions without end operations skip scope creation on end; actions whose start ops are provably synchronous cannot overlap, enabling simpler generated code, but the ordering contract must hold generally.

#### How the engine starts and ends TimelineActions

Events are precomputed per timeline as sorted schedule entries {action,isStart} (eligius-engine.ts: _timelineSchedules used at 1620-1700). _dispatchActionsBetween(from,to) (approx. lines 1620-1700): for forward moves it collects actions whose start boundary is crossed (not active, not pending) into pending starts and actions whose end is crossed (active) into ends; for backward moves it processes events in reverse: crossing a start ends the action (if active), crossing an end restarts the action if it covers `to` (sorted by start ascending); big forward jumps (> _maxCatchUp) become _reconcileActions (like a seek). _runEndsThenStarts runs all ends FIRST (each through _runActionMethod, not awaited sequentially, in schedule order), then starts only after ends and any earlier start gate settle (a Promise gate), else immediately; `endAfterStart` pending flag ends an action right after its start when its whole range was crossed in one update (1585-1595 region, 1740-1745). Starts do not await action completion (_runActionMethod returns after settle but dispatch does not await). Timeline completion/stop end all active actions highest-start-first and sequentially awaited (_endActiveActionsReporting, eligius-engine.ts:1480-1489; destroy ends active then init actions reversed, 1171-1191, 1265-1272). Init actions are started sequentially with `await action.start()` during init(), and their end() is called on destroy in reverse order (946-952, 1189-1191). Initial `operationData` for engine-driven start/end is always undefined (-> {}). Action `duration` {start,end} are numbers in seconds, validated end>=start at resolve (configuration-resolver.ts:700-705).

**Static or dynamic:** Scheduling stays runtime (H2). Compiled action bodies would be wrapped in objects implementing ITimelineAction (start/end/active/duration/name/id) so the engine is unchanged.

#### Action id/name, registry and operation resolution

IResolvedOperation.instance is the imported operation function, looked up by systemName through the importer (configuration-resolver.ts:527-561) which also rejects classes/controllers (describeNonOperation). Action names must be unique across actions and eventActions (configuration-resolver.ts:460). Event actions are plain `Action` (configuration-resolver.ts:487) holding only startOperations; timeline and endable actions come from resolveTimelineAction/resolveActions (724-760). Custom operations registered through EligiusResourceImporter({operations}) are ordinary functions with the same TOperation contract and may use `this` arbitrarily; compiled code must call them with `this` set to a scope-like object that satisfies IOperationScope.

**Static or dynamic:** Operation function identity is static after resolution if the importer is known at compile time; custom operations require the compiler to emit imports or a runtime registry lookup.

#### Existing test-helper evidence: operations are decoupled enough to call directly

util/apply-operation.ts provides createDefaultScope ({currentIndex:-1, eventbus:{}, operations:[]}) and applyOperation(operation, data, scope) = operation.apply(scope,[data]), used by operation specs. **Static or dynamic:** Static: direct call is possible.

### Compiler implications

- MUST reproduce exactly: the data-flow contract. Output of op N (or {} if undefined/null) becomes the input of N+1 after Object.assign(prevOutput, deepCopyIfNested(configuredData)); configured keys overwrite incoming same-named keys. A compiler can keep ops as external function calls (`d = Object.assign(d, cfg())`; `r = op.call(scope, d)`) and still get most benefit; inlining ops requires per-op knowledge of erased/added keys.
- MUST reproduce per-execution freshness of nested configured data (action.ts:352-360), including cycles/class instance retention semantics of deepCopy, or prove no downstream op mutates nested values. Primitive-only configured data can be hoisted to constants (still must be merged key-by-key into the flowing object).
- CAN eliminate at compile time: when/otherwise/endWhen/forEach/endForEach/break/continue index searches (findNextFlowControlIndex, findEndWhenIndex, findEndForEachIndex, findEnclosingEndWhenIndex) become structured if/else/for/continue/break; the scope-stack push/pop and WeakMap lookups (loopCollections, pendingLoopJumps, _loopOperationData); expression parsing (parseExpression per execution) becomes a compiled JS expression; proto-key walk (assertNoProtoKeys) and forbidden-segment checks for static chains can be done at build time.
- MUST preserve for loops: collection resolved once then slice()d; loopLength = last index; `$scope.currentItem/loopIndex/loopLength/loopStartIndex/loopEndIndex` observable by chains and customFunction; `collection` key stays in operationData and is re-assigned every iteration from the cached configured object; operationData object carries across iterations; empty/null collection runs no body but endForEach still executes; break clears loop fields so post-loop `$scope.loopIndex` is undefined; continue on last iteration ends the loop.
- MUST preserve for when: evaluation uses the MERGED operationData, `expression` removed afterwards, whenEvaluation lives on the when's own scope and is deleted by endWhen; truthiness rules ('false' string truthy), strict ==, short-circuit, throw-on-null-intermediate chains; else branch semantics via otherwise executing even when when was true (it just jumps).
- MUST preserve async semantics: sync ops run synchronously up to the first promise; each promise result is awaited and the resolved value becomes next input; conditional promises (customFunction, invokeObjectMethod, addControllerToElement) require dynamic `isPromise` checks (or an always-async body that accepts the ordering change; this can reorder TimelineAction start/end interleave and eventbus handler timing because TimelineAction.finish relies on synchronous completion, timeline-action.ts:92-122). Recommended: generate a function that returns a promise only when needed, or a hybrid with a sync fast-path.
- MUST preserve error contract: first failing op aborts the run, error is annotated with operationSystemName/operationIndex (keep the ORIGINAL index in the source operations array, not the compiled position), non-Errors wrapped with cause, existing annotation not overwritten, no cleanup/rollback, async rejection annotated with the op that returned the promise.
- MUST keep a scope object (or equivalent) for any op that reads `this`: at least {eventbus, operations, currentIndex} (operations/currentIndex used for error naming by getCurrentOperationName and by loop-jump when computing endWhen index at runtime), plus variables/currentItem/loop*/whenEvaluation/parent chain when `$scope.` chains, setVariable, setData or customFunction appear in the action. A compiler can analyse an action for `$scope.` usage and customFunction/`$scope.newIndex`; if absent it can elide the scope chain and keep only a minimal scope. setVariable semantic: variables are per RUN and live on the ROOT scope, shared by all nested blocks, NOT shared between start and end runs of the same EndableAction.
- MUST treat start and end runs as separate programs with separate scope/variables and with end() starting from {} unless a caller passes data (startAction/endAction/event). Generated code for an EndableAction therefore produces two functions; state shared between start and end must flow through globals (setGlobal/setGlobalData), DOM, or controller instances, never through locals.
- MUST keep TimelineAction wrapper semantics (active flag flips synchronously, start/end serialised, second start/end is a no-op, finish on both success and failure). Easiest: generated start/end functions are installed into the existing TimelineAction/EndableAction classes (e.g. a subclass that overrides _runOperations), leaving the engine untouched.
- MUST fall back (interpreter or state-machine-over-indices) or reject when it sees `$scope.newIndex` in setData properties (set-data.ts:34-37,259-262), customFunction (can set newIndex via this), or any op that writes arbitrary scope jumps; unbalanced when/forEach structures (missing endWhen/endForEach, stray endForEach) have defined-but-odd behaviours (jump to operations.length, root scope pop TypeError) the compiler should either reject at compile time (with JSON path) or emulate.
- CAN resolve statically: requestAction target names to action references when the closed set of actions is known, but the runtime uses a name registry via eventbus request and throws at the requestAction op; keep that error timing (fail at runtime op, or fail at compile time with a clear message as a deliberate behaviour change).
- Operations that return new objects (wait, startAction, endAction, setOperationData, invokeObjectMethod, async customFunction) break object identity of the flowing data; a compiler using local variables per key must model these identities or simply keep a single `d` variable and reassign it with each op result like the interpreter does.

### Hazards

- Object.assign(operationData, configuredData) mutates the PREVIOUS op's returned object (action.ts:181-184); an op that returns an object it also stored elsewhere (e.g. a controller holding operationData, since addControllerToElement passes operationData to controller.init, add-controller-to-element.ts:54) will observe later merged keys. Copying data at each step in generated code would change behaviour.
- Configured nested objects are deep-copied on every execution but flat primitive-only configured objects are NOT copied (only merged key-by-key) - generating a shared constant for a nested value (instead of a fresh literal) leaks mutations between executions.
- Sync return of undefined/null silently resets operationData to {} (action.ts:237), and a promise resolving to undefined/null does the same (145,149): custom operations that forget to return data wipe the chain.
- loopLength is the last index (length-1), not the length (for-each.ts:49); `$scope.loopLength` consumers and the endForEach test `loopIndex < loopLength` depend on that.
- forEach re-executes as an operation each iteration and re-merges the cached configured data, re-adding `collection` to operationData every iteration; configured data is not re-deep-copied per iteration (cached object reused, action.ts:176-180,194).
- The snapshot is a SHALLOW slice at loop start: later changes to the source array (push/remove) are invisible but mutation of item objects is visible. Collection resolved by `$globaldata` chain is a deep copy already, `$operationdata`/`$scope` chain values are references.
- when's false branch jumps TO the otherwise/endWhen operation (which then executes) rather than past it; true branch hits `otherwise` and jumps to endWhen. An `otherwise` outside a when scope sees whenEvaluation undefined and does nothing (falls through), no error.
- endWhen and endForEach pop positionally; unbalanced structures pop the root scope and crash with a TypeError on the next iteration instead of a clear message (action.ts:156-157).
- Break/continue inside when-blocks do not jump directly to endForEach; they hop through each enclosing endWhen (loop-jump.ts). Skipped code includes `otherwise` bodies but the intermediate endWhen ops still run (whenEvaluation deleted). A compiler emitting a plain JS `break`/`continue` is equivalent only if it also reproduces the side effects of endWhen (delete whenEvaluation) - harmless unless `$scope.whenEvaluation` is observed - and the loop-field deletions on break.
- Child scopes proxy only currentIndex/eventbus/operations to the parent; everything else is own-property. `$scope.x` lookups use `x in scope` walking `.parent`, so deleting a loop field makes an outer scope's same-named field visible (e.g. nested forEach: inner `loopIndex` deleted after break exposes outer loop's loopIndex only if the inner scope is still the TOP scope, i.e. between break and the popping endForEach).
- getCurrentOperationName reads scope.operations[scope.currentIndex].systemName, so error messages depend on currentIndex being the index of the executing op in the ORIGINAL operations array; a compiler that flattens or reorders must still pass the right name.
- A thenable-returning operation is detected by isPromise (any thenable); customFunction ignores non-thenable return values but a returned promise is awaited and its resolved value is dropped (internalResolve(resolve,{},operationData), custom-function.ts:66-68) - note the data is rebuilt as a NEW object copy of operationData in the async path but the SAME object in the sync path.
- startAction/endAction always yield a microtask even when the callee is synchronous, and TimelineAction.start returns Promise.resolve({}) immediately when already active, in which case the caller continues with its own data and the callee ops do NOT run.
- TimelineAction._active is not rolled back when start fails; and a failing start ops chain leaves the run in whatever state with no cleanup, so a subsequent end() runs end ops against a half-built DOM.
- Variables set via setVariable are per run (per start or per end invocation) and not shared between start and end runs of the same action; code generators mapping them to closure variables of the whole action would be wrong.
- `when` and others parse/validate lazily at first execution: malformed expressions or bad chains currently fail at runtime, not at load. Compile-time validation would be a behaviour improvement but changes timing of failures.
- Property-chain `+suffix` and bracket-index rewriting (`a[0].b` -> `a.0.b`) and the global-object/forbidden-segment guards are part of semantics (get-property-chain-value.ts:46-84); a naive `a?.b` translation would not throw on null intermediates and would diverge.
- My enumeration of scope readers is grep-based on `this` in src/operation/*.ts; operations are plain functions, so any custom operation registered via the importer can use any scope field.

### Hypothesis verdicts

H1 (interpreter overhead small / wins elsewhere): PARTIALLY SUPPORTED by this area. The executor does real per-step work, but only at action boundaries: per operation one Object.assign, one copyConfiguredOperationData (WeakSet check; a full structuredClone-style deepCopy only when nested config values exist, action.ts:344-363, and the deep copy happens EVERY execution), one `.call`, plus for when parseExpression every execution (when.ts:92), indexOf-style forward scans (findNextFlowControlIndex, findEndForEachIndex via operations.slice, for-each.ts:114-129; otherwise.ts:19-34) and property-chain regex/split/flatMap/assert per chain (get-property-chain-value.ts:46-53). forEach adds a per-iteration re-merge and re-execution. None of this runs per tick (ticks only range-check, eligius-engine.ts:1620-1700), so the cost is O(ops) per action start/end, and loops multiply it by iteration count. Compilation removes parse/scan/scope-stack/deepCopy overhead but the operations themselves (jQuery DOM, animation, controllers) dominate. The real remaining costs that compilation does NOT remove: `Promise` allocation per run, per-op async boundaries, jQuery. So H1 is plausible for most presentations; loops over big collections and deeply nested configured data are the exception where compilation could give a measurable speedup.
H2 (only action/operation layer compiles): STRONGLY SUPPORTED. The action layer is cleanly encapsulated behind IAction/IEndableAction/ITimelineAction (action/types.ts:5-20): the engine only calls start()/end(), reads `active`, `duration`, `name`, `id` (eligius-engine.ts:1497-1506, 1620-1700). Compiled bodies can be installed as drop-in replacements for _runOperations or as objects implementing ITimelineAction. Scheduling, active/queue semantics (TimelineAction), eventbus registry (request-action), and error reporting (EngineActionError) stay runtime. requestAction/startAction/endAction depend on a runtime registry via the eventbus (engine-factory.ts:155-197).
H3 (runtime-dynamic values stay dynamic): STRONGLY SUPPORTED. Chains into `$operationdata`, `$globaldata` (deep-copied), `$scope`, event args (`eventArgs` in operationData), forEach over runtime arrays (collection resolved at loop start, snapshot), when on runtime values all resolve at execution time via resolveExternalPropertyChain; control-flow structure (jump targets, nesting) is fully static and compiles to if/for, but values and promise-vs-sync of several ops are dynamic. One extra counter-point: `$scope.newIndex` writes and customFunction `this` scope access (set-data.ts:34-37; custom-function.ts:28-31) make some actions non-structurally-compilable (arbitrary goto), forcing a fallback.

## data-resolution: Operation data resolution: how configuration values become runtime values (property-chain syntaxes, when-expression grammar, globals, scope, copy/mutation/erasure semantics, prototype-pollution guards). All paths are relative to F:\projects\eligius\eligius\src.

There is no general-purpose templating or interpolation layer. Operation data flows as ONE mutable plain object per action run. Before each operation the interpreter does `Object.assign(flowingData, configuredData)` (action/action.ts:181-184), so configured keys overwrite same-named keys produced earlier. The operation is then called with `this` bound to a scope object (action.ts:197-200). Its return value (or `{}` if undefined, action.ts:237) becomes the next operation's input. Each start/end run begins from `{}` (action.ts:145,149) unless the caller passes init data: event actions pass `{eventArgs: [...args]}` (eventbus/actionregistry-eventbus-listener.ts:50), controllers pass their own data, and `startAction`/`endAction` pass merged data. End operations do NOT inherit start-operation data (endable-action.ts:26-32 plus the fresh `{}`).

Resolution of `$`-chains is NOT done by the engine. It is opt-in, hard-coded inside about ten operations, each of which resolves only specific fields. All other operations receive the literal string, e.g. `addClass.className:'$operationdata.x'` stays a literal. The resolving sites are:
- `when`: expression operands.
- `forEach`: `collection`, only when it is a string.
- `selectElement`: `selector`.
- `setData`: the values; the target keys are parsed separately.
- `setOperationData`: `properties`, deep.
- `setStyle`: `properties`, deep.
- `createElement`: `elementName`, `attributes` (deep) and `text`.
- `calc`: `left`, `right`, `operator`.
- `math`: `args` (deep) and `functionName`.
- `broadcastEvent`: `eventArgs`, top-level array elements only.

Only three runtime prefixes exist (`$operationdata.`, `$globaldata.`, `$scope.`, case-insensitive, whole-string match, resolve-external-property-chain.ts:132-141). There are NO `@` prefixes and no interpolation of a chain inside a larger string. Three further syntaxes are resolved once at configuration-load time by `ConfigurationResolver`, before any action runs: `template:<name>`, `json:<name>`, `config:<path>` (configuration/configuration-resolver.ts:766-935). Operations and controllers are referenced by `systemName` strings that the resolver turns into function references (resolver.ts:526-566). `customFunction` and `getImport` look up host code at RUNTIME through an eventbus `request-function` request (custom-function.ts:48-53, get-import.ts:43-47, helper/request-registered-entry.ts:19-76).

For every syntax the PATH is static, because it is parsed from config text and can be validated at compile time. The VALUE is runtime, because it depends on earlier operations, event args, the global store or scope state. The `config:`, `template:` and `json:` forms are fully compile-time resolvable if the importer's resources are available to the compiler.

The `when` grammar is a tiny, side-effect-free, precedence-climbing expression language that lowers cleanly to a JS expression with short-circuit semantics (parse-expression.ts, parse-operand.ts). Notably the interpreter re-tokenizes and re-parses the expression on EVERY execution (when.ts:92, no cache). Together with the per-execution deepCopy of nested config data and of `$globaldata` reads, and the `split`/`flatMap`/regex work per chain resolve, this is the real, avoidable interpretive overhead in this layer. A compiler could remove it, but the observable semantics listed in `findings` and `hazards` must be reproduced.

### Findings

#### Per-operation merge: configured data overwrites flowing data (core data-flow primitive)

action/action.ts:175-184: `configuredData = (isLoopIteration ? this._loopOperationData.get(scope) : undefined) ?? copyConfiguredOperationData(operationInfo.operationData, systemName)`, then `mergedOperationData = Object.assign(operationData, configuredData)`. This MUTATES the object returned by the previous operation (and the init-data object the caller supplied; controllers rely on it via Object.assign back, controllers/helper/controller-actions.ts:101-103). Config keys WIN over same-named keys produced earlier. The operation then runs with that same object as its argument (action.ts:197-200), so `$operationdata.<ownConfigKey>` inside an operation sees the raw configured value, e.g. `calc` with `left:'$operationdata.left'` resolves to the unresolved string. The return value is used as the next input; `undefined`/null becomes `{}` (action.ts:237), silently dropping all accumulated data. A promise result is awaited and its resolved value passed on (action.ts:212-234); a resolved `undefined` becomes `{}` via the default param/`??` at action.ts:145,149.

**Static or dynamic:** Key SET is static in most cases (config keys are known), but the flowing object's full shape is only partially knowable: custom functions mutate it arbitrarily (custom-function.ts:61), `clearOperationData`/`removePropertiesFromOperationData`/`setGlobalData`/`addGlobalsToOperation` take literal name lists (static), init data (`eventArgs`, controller data) is runtime. A compiler can track keys statically up to the first opaque customFunction or unknown-init-data and use a plain bag object beyond that.

#### Configured data copy rules (when nested config is deep-copied)

configuration-resolver.ts:559 deepCopy()s `operationData` once at resolve time. At each execution `copyConfiguredOperationData` (action.ts:344-363) returns `emptyOperationData` (frozen `{}`, action.ts:279) if undefined, otherwise runs `assertNoProtoKeys` (cached per object in a WeakSet, action.ts:286-330), and then: if ANY own top-level value is a non-null object it returns `deepCopy(operationData)` (a fresh deep copy on EVERY execution, action.ts:352-360); if the data holds only primitives/functions it returns the configured object itself (safe because Object.assign copies top-level keys). forEach: the configured data is copied once when the loop starts, stored in `_loopOperationData` keyed by the loop scope, and re-merged each iteration without re-copying (action.ts:173-195, 27). Consequence: operations may freely mutate nested config arrays/objects for that execution only (e.g. removePropertiesFromOperationData pushes onto `propertyNames`, remove-properties-from-operation-data.ts:22-24) without corrupting the next run. Within a forEach, however, the same nested objects are shared across iterations (the single loop copy).

**Static or dynamic:** Static: which operations have nested config objects is known at compile time. A compiler can hoist immutable nested literals ONLY when the consuming operation never mutates or leaks them; otherwise emit a fresh literal per execution (object/array literal inside the function body is the natural way to preserve this) and a per-loop (not per-iteration) literal for forEach config.

#### deepCopy semantics

helper/deep-copy.ts:34-85. Primitives and functions are returned as-is. Arrays and plain objects (isPlainObject, cross-realm safe) are copied recursively with cycle preservation via a WeakMap (`seen`) and keys copied with defineProperty so an own `__proto__` stays a data property (deep-copy.ts:62-76). jQuery objects (`.jquery` is a string) and DOM `Node`s are kept BY REFERENCE (isReferenceOnly, 87-92). Date, RegExp, Map, Set, Error, ArrayBuffer and typed arrays are copied with structuredClone (97-112; fallback to JSON round trip if structuredClone is missing, 11-14). Everything else, i.e. class instances such as controllers, actions, the eventbus, is kept by reference (78-80). `deepCopy(undefined/null)` returns it unchanged (isDefined, 35-38). Only `Object.keys` own enumerable string keys are copied (no symbols, no non-enumerables, no getters preserved as getters).

**Static or dynamic:** Dynamic by nature (depends on runtime value types) for copies of runtime values (`$globaldata`, globals); static for config-literal copies (known to be JSON-like). A compiled `deepCopy` call must keep this exact type-dispatch for runtime values. For config literals the compiler can emit a literal.

#### Property-chain syntax: the complete list

Recognised chain strings (resolve-external-property-chain.ts:132-141, 143-146): case-insensitive prefix `$operationdata.`, `$globaldata.`, `$scope.` (isExternalProperty uses toLocaleLowerCase().startsWith). The prefix is split off and lower-cased (resolve-external-property-chain.ts:40-41). Remaining dotted path is resolved by getPropertyChainValue (get-property-chain-value.ts:34-87). There is NO `@` syntax, NO `${}` templating, NO function-call syntax, NO string interpolation (`'Hello $operationdata.name'` is a literal). Beyond the basic dotted path, segments support: (a) bracket-digit indices `a[0]` / `a[2].b` are expanded to `a.0` / `a.2.b` BEFORE lookup (get-property-chain-value.ts:46-51; only `[digits]`, other brackets stay literal parts of the key); (b) a `+suffix` on the LAST segment: `width+px` reads `width` and returns `${value}px` (73-78, 86). Only the first '+' split is used (`parts[1]`), `a+b+c` gives suffix 'b'; an empty suffix (`a+`) is falsy so the suffix is dropped and the raw value returned; (c) empty segments are dropped (`.filter(part => part.length>0)`, line 50) so `$operationdata.a..b` == `a.b` and `$operationdata.` (empty path) returns the SOURCE OBJECT ITSELF (reduce over an empty chain, no global-object check since chain.length is 0, line 82). In `when`, the stricter `chainPattern` additionally requires non-empty segments with no whitespace/quotes (parse-operand.ts:20-21), so these edge cases are reachable only through the non-expression resolvers.

**Static or dynamic:** Path parsing, segment validation, prefix selection, bracket expansion and suffix split are fully static (can be done once at compile time, including the forbidden-segment check). The lookup VALUE is runtime.

#### Per-prefix resolution semantics

`$operationdata.x.y`: walks the CURRENT flowing operationData object (which already contains this operation's own merged config) by `currentInstance[prop]`, no copy, no own-property check, so inherited/prototype members like `length`, `toString` ARE readable (only __proto__/prototype/constructor are blocked). Returns the live reference (resolve-external-property-chain.ts:49-50). `$globaldata.x.y`: walks `getGlobals()` which with no name returns the LIVE null-prototype cache (globals.ts:5,12-13,53), then the FINAL value is `deepCopy`'d (resolve-external-property-chain.ts:51-54) so callers never alias the store. `$scope.x.y`: resolved against the nearest scope (current scope, then walking `.parent`) that declares the head property via `head in scope` (resolve-external-property-chain.ts:81-89, 103-115); if none declares it, it falls back to the current scope so the standard 'cannot be resolved' error fires. Scope heads that exist in practice: `variables`, `currentItem`, `loopIndex`, `loopLength` (this is length-1, NOT the length: for-each.ts:49), `loopStartIndex`, `loopEndIndex`, `newIndex`, `currentIndex`, `whenEvaluation`, `owner`, `parent`, `eventbus`, `operations` (types.ts:8-62). null/undefined input returns null, a non-chain value is returned unchanged (resolve-external-property-chain.ts:32-37, 60).

**Static or dynamic:** Prefix and path: static. `$operationdata` / `$globaldata` values: runtime. `$scope.variables.*`: runtime values, but the DECLARING scope is a lexical-structure question that the compiler can mostly answer statically (variables live on the action root scope, set by setVariable; loop vars on the nearest enclosing forEach). Caveat: it is dynamic by presence (`in`), see hazards about deleted loopIndex/currentItem shadowing.

#### Error behaviour of chain resolution

getPropertyChainValue throws `Error` when an intermediate is null/undefined: `<op>: property chain '<chain>' cannot be resolved: '<resolvedPart>' is <null|undefined>.` (get-property-chain-value.ts:62-66). Falsy non-nullish intermediates ('' / 0 / false) are valid and indexable (comment at 60-61). A final value of undefined is NOT an error (no check on the leaf), e.g. `$operationdata.missing` yields undefined. Forbidden-segment error: `<op>: property chain '<chain>' contains forbidden segment '<seg>'. Property chains may not contain __proto__, prototype or constructor.` (assert-safe-property-chain.ts:47-49). Global-object error: `... reaches the global object at '<part>'. Property chains may not access the global object.` (get-property-chain-value.ts:89-95). The operation name prefix comes from `getCurrentOperationName(scope)` = `scope.operations[scope.currentIndex].systemName` (assert-safe-property-chain.ts:55-59), so the message is only prefixed when the scope knows the operation list. Errors are annotated with `operationSystemName` and `operationIndex` (index in the action's operation array including control-flow ops) by `withOperationContext` and rethrown/rejected (action.ts:239-245, 265-277); the engine reads these to build `EngineActionError`. The innermost annotation wins (action.ts:272-275).

**Static or dynamic:** Error TIMING is dynamic: everything throws at execution of the operation, not at config load. Forbidden-segment errors are statically detectable; a compiler may promote them to compile errors (behavior change: fail fast vs fail when reached; note that `when` short-circuiting can skip a bad chain at runtime, parse-expression.ts:308-317).

#### resolvePropertyValues (deep resolution used by setOperationData, setStyle, createElement, calc, math)

helper/resolve-property-values.ts:32-53. If `newProperties !== operationData` (always the case in shipped operations) it first `deepCopy`s newProperties (line 37-38); every shipped caller passes a separate object, so the documented in-place branch is effectively dead code. It then iterates `Object.keys(target)` top-level and calls resolveValue (59-107), which: replaces a whole-string chain with the resolved value (64-66); leaves primitives, class instances, jQuery, DOM nodes untouched and unwalked (67-73); recurses into arrays and plain objects copy-on-write with cycle guard `visiting` (75-106). Keys are never resolved, only values. Results are inserted BY REFERENCE for `$operationdata` and `$scope` (no copy) but as a deep copy for `$globaldata`. Calling with undefined/null `newProperties` throws a native TypeError from Object.keys (e.g. setStyle with no `properties`).

**Static or dynamic:** Which positions contain chains is static (config literal walk). Values: runtime. A compiler can emit an object literal with direct reads at chain positions, e.g. `{elementName: get(...), attributes: {id: get(...)}}`, and skip the entire deepCopy+walk. Must keep reference-vs-copy semantic per prefix.

#### setData: targets, assignment and aliasing

set-data.ts:52-118. `properties` keys are target chains, values are source chains or constants. The root target is computed as `path.shift().toLowerCase().substring(1)` (line 70): the FIRST CHARACTER is dropped without checking it is '$', so 'xscope.foo' also works. Allowed roots: scope, operationdata, globaldata (120-123) else `Unrecognized target: <root>, known targets are: scope, operationdata, globaldata`. `assertSafePropertyChain(path, item, 'setData')` checks every segment incl. the written property (80). #### Globals store

helper/globals.ts. A module-level singleton `cache = Object.create(null)` shared by ALL engines on the page (line 5, doc 67-72); cleared when the last EngineFactory engine is destroyed (engine-factory.ts:288-289). `getGlobals()` with no name returns the live cache; `getGlobals(name)` returns `Object.hasOwn(cache,name) ? cache[name] : undefined` and deepCopies only TRUTHY values (falsy values such as 0/''/false/null are returned as-is, lines 12-15). `setGlobals(obj)` asserts the name is not __proto__/prototype/constructor (assertSafeGlobalName, 38-44) and stores `deepCopy(value)` (18-23). `setGlobal(name,value)` stores BY REFERENCE (set-global.ts:8-12) and `removeGlobal` deletes (remove-global.ts:3-6); neither of those is used by any shipped operation (grep shows only definitions). #### @erased: what it means at runtime

`@erased` is only a doc tag. The metadata generator turns it into `erased: true` in generated parameter metadata (tools/code-generator/metadata-generator.ts:256-259) and the schema generator strips it from docs (tools/schema-tools/generate-schemas.ts:212,372); the interpreter does not read it. The real behavior is hand-written in each operation, and the operation's return type is `Omit<Data, erased keys>`. Runtime erasure mechanisms: (1) `removeProperties(operationData, ...keys)` = `delete` on the very object received (remove-operation-properties.ts:31-39; used by ~49 of 81 operation files); (2) raw `delete (operationData as any).x` (get-import.ts:41, clear-operation-data.ts:293, invoke-object-method.ts:64-65); (3) rest destructuring that returns a NEW object without the erased keys (wait.ts:261-265, start-action.ts:32-36, end-action.ts:85, set-global-data.ts:27, invoke-object-method.ts:62 plus mutate-delete, math.ts:53-57, set-operation-data.ts:27); (4) filter-by-name rebuild (remove-properties-from-operation-data.ts:21-30, which also mutates the config-supplied `propertyNames` array and always erases `propertyNames` itself). An automated cross-check of every `@erased` property against these mechanisms found a mismatch only for `removePropertiesFromOperationData.propertyNames` (erased through the filter, not delete). Erasure happens at a point the operation chooses, which can be BEFORE a later throw (e.g. calc erases left/right/operator at calc.ts:67, then validates the operator at 69-73; when erases `expression` at when.ts:95 after evaluation). Erased keys can be re-introduced by the next operation's config merge.

**Static or dynamic:** Static per operation (the erased set is fixed by the op implementation and by the generated metadata). For built-in ops the compiler can track key presence/absence precisely and replace `delete` with local-variable liveness. Because the tag is not authoritative (hand-written), use a hand-verified per-operation table or the cross-check script as a conformance test.

#### New-object vs in-place return (aliasing differences between operations)

Operations differ in whether they return the same object they received or a new one. In-place (same reference): most DOM operations, calc, selectElement, createElement, setStyle, setData, getImport, addGlobalsToOperation (Object.assign), clearOperationData with a property list (clear-operation-data.ts:291-297), mapArray, log. New object: wait (wait.ts:261), startAction/endAction (start-action.ts:49, end-action.ts:100 builds `{...callerOperationData}`), invokeObjectMethod (returns `newOperationData` rest-copy, but ALSO deletes methodName/methodArguments from the old object, invoke-object-method.ts:62-65,118), setGlobalData, setOperationData (returns `{...newOperationData, ...resolvedProperties}` or `resolvedProperties` when `override`, set-operation-data.ts:35-42), math (math.ts:53-77), clearOperationData without list (`{}`, line 299), removePropertiesFromOperationData, customFunction when the function returns a promise (`internalResolve(resolve, {}, operationData)` merges into a NEW object, custom-function.ts:65-69; the synchronous path returns the same object and IGNORES the function's return value, 61-72). Observable only through object identity (e.g. a customFunction or listener holding a reference to the earlier data object) and through the Object.assign-into-previous-result mutation in action.ts:181. Data passed by `startAction` is also merged: `mergeOperationData(a,b)` = `{...a, ...b}` (merge-operation-data.ts:3-8), `internalResolve` (internal-resolve.ts:4-14).

**Static or dynamic:** Static per operation. For compiled code the data object identity is mostly unobservable, EXCEPT for customFunction (user code receives the object and may mutate it, keep a reference, or add arbitrary keys) and for the controller path that Object.assigns results back into its own object.

#### The when expression grammar (complete) and its lowering to JS

Grammar (parse-expression.ts:67-75), lowest to highest precedence: `or := and ('||' and)*`; `and := comparison ('&&' comparison)*`; `comparison := unary (('=='|'!='|'>='|'<='|'>'|'<') unary)?` (NON-associative: a second comparison operator is a parse error with hint, 192-201); `unary := '!' unary | primary`; `primary := '(' or ')' | operand`. Tokenizer (210-252): whitespace skipped; symbols matched longest-first from ['&&','||','==','!=','>=','<=','>','<','!','(',')'] (34-46); a lone '=', '&' or '|' is an error with 'Did you mean' (228-232); an operand starting with `'` is a quoted string that ends only at a quote followed by whitespace/operator/paren/end (endOfString 258-265), so apostrophes inside text work and operators inside quotes are text, there are NO escape sequences; otherwise a word ends at the first delimiter char `[\s()!=<>&|]` (endOfWord 267-273, delimiterPattern 58). Operands (parse-operand.ts:49-74), tried in this order: quoted string `^'(.*)'$` (dot-all; value = inside text raw), keywords `true`/`false`/`null` via Object.hasOwn(keywords) (lowercase only), number `^[-+]?(\d+(\.\d*)?|\.\d+)([eE][-+]?\d+)?$` -> Number(token), chain `^\$(operationdata|globaldata|scope)\.[^\s.'"]+(\.[^\s.'"]+)*$` (case-insensitive). Anything else throws `<op>: unknown operand '<tok>' in expression '<expr>' at position N. Use a number, ...`. Empty/non-string expression throws (100-109). Evaluation (290-336): `evaluateExpression` returns `Boolean(evaluateNode(...))`. 'operand' -> its value; 'not' -> `!v`; 'and'/'or' -> `Boolean(l) && Boolean(r)` / `Boolean(l) || Boolean(r)` with real JS short-circuit (so the right chain is not read, and cannot throw, when the left decides); comparison -> `==` is strict `===`, `!=` is strict `!==`, `<`,`<=`,`>`,`>=` are raw JS relational operators on whatever types (string vs number coercion, undefined comparisons are false). Because `null` is a keyword literal and `==` is strict, `$operationdata.x==null` is FALSE when x is undefined. `!` binds tighter than comparison (`!$a==1` is `(!$a)==1`). Lowering is straightforward: each comparison -> `(L === R)` with parentheses (JS has separate precedence for equality and relational operators, the grammar does not), and/or -> `(Boolean(L) && Boolean(R))`, not -> `!L`, chain -> accessor expression, string literal via JSON.stringify of the raw inner text, number via the parsed Number, keywords as JS literals. The result must be coerced to boolean exactly as the interpreter does.

**Static or dynamic:** Fully static parse (all syntax errors become compile-time errors; note the behavior change that the interpreter reports them only when the `when` op executes, since it parses on every execution with no cache, when.ts:92). Only operand VALUES and the resulting boolean are runtime.

#### when / otherwise / endWhen runtime control-flow semantics

Action pushes a NEW child scope before invoking `when` (action.ts:186-187) via _pushScope: getters/setters proxy `currentIndex`, `eventbus`, `operations` to the parent and `parent` is set (110-131). `when` evaluates against the merged data and the child scope, erases `expression` (when.ts:95), sets `this.whenEvaluation` (97), and if false sets `this.newIndex = findNextFlowControlIndex(this)` (99-101), i.e. the index of the matching `otherwise` or `endWhen` at the same nesting depth (110-127, depth counts nested when/endWhen only; returns operations.length if unmatched). `otherwise`: if `this.whenEvaluation` is truthy, jump to the matching endWhen (otherwise.ts:13-15, 19-34). `endWhen`: `delete this.whenEvaluation`, then `continuePendingLoopJump` (end-when.ts:46-47); the interpreter pops the scope when it executes endWhen (action.ts:202-208). A jump (newIndex) is consumed at the START of the next loop turn (action.ts:157-160) and the target operation itself then executes (when false and an `otherwise` exists, the otherwise op runs and falls through; because its whenEvaluation is false it does not jump). The flowing operation data is unchanged by skipping, except `expression` was erased; operations in the skipped region contribute NOTHING, not even their config merge. Malformed nesting is tolerated rather than rejected: unmatched `when` skips to the end of the action; a stray `endWhen` would pop the root scope and then crash on `scopeStack[length-1]` (action.ts:156,207) ; `otherwise` without `when` is a no-op.

**Static or dynamic:** Block structure (matching of when/otherwise/endWhen/forEach/endForEach) is static and can be turned into if/else and for. The condition value is runtime. The compiler must reject (or define behavior for) crossing/unbalanced blocks that the interpreter silently accepts, since they cannot be expressed as structured JS.

#### forEach / endForEach / break / continue state

On first execution (`this.loopIndex === undefined`, for-each.ts:40) it resolves the collection ONCE (41-45; string -> chain, non-string used as-is; non-array non-nullish throws 'forEach: Expected resolved collection property to be array type, string value was probably not resolved correctly', 102-110), finds the matching endForEach (`loopEndIndex`, 46, search lines 114-129, defaults to operations.length), and if non-empty sets `loopIndex=0`, `loopLength=length-1` (the last INDEX, not the length), `loopStartIndex=currentIndex` and stores a shallow `slice()` snapshot in a module WeakMap (47-53), so mutation of the source array during the loop does not affect it. Empty/null/undefined collection: `newIndex=loopEndIndex` and loop props deleted (54-62). Every execution then sets `this.currentItem = snapshot[loopIndex]` (65-68). `forEach` does not erase `collection`, it stays in the flowing data during and after the loop. `endForEach` (end-for-each.ts:61-73): if more iterations, `loopIndex++`, `newIndex = loopStartIndex` (so the forEach op itself re-executes every iteration and re-merges its configured data from the cached loop copy), `delete currentItem`; otherwise clears the snapshot; the interpreter pops the loop scope when `newIndex` is undefined (action.ts:202-208). `breakForEach` / `continueForEach` -> requestLoopJump (helper/loop-jump.ts:144-156): the jump is applied directly if the break is in the loop scope itself; inside nested `when` blocks it sets `newIndex` to the enclosing endWhen first and records a pending jump that endWhen continues (163-184, 186-203); `applyLoopJump` sets `loopScope.newIndex = loopEndIndex`, deletes `currentItem`, and for 'break' also deletes loopIndex/loopLength/loopStartIndex/loopEndIndex and the snapshot (205-216). Net effect equals plain structured `break`/`continue`. Data produced inside an iteration persists into the next iteration (single flowing object) unless erased, and persists after the loop. The scope-chain read of `$scope.loopIndex` after an inner `break` deletes the inner `loopIndex` falls through (by `in`) to an outer loop's `loopIndex`.

**Static or dynamic:** Structure static. Collection resolved at runtime ONCE at loop start. A compiled `for` must iterate a snapshot (`slice()`) of the resolved array, expose `loopLength` as length-1 if `$scope.loopLength` is referenced, and keep last-iteration side effects (currentItem deleted/undefined-after) only if referenced.

#### Variables and scope reads/writes

setVariable (set-variable.ts:38-61): rejects names `__proto__`/`prototype`/`constructor`; writes to the nearest scope that has `variables`, else creates `variables = Object.create(null)` on the ROOT scope (`findDeclaringScope('variables', this) ?? findRootScope(this)`, lines 50-54); `value` is stored verbatim without chain resolution; erases `name` and `value` (58). Reads via `$scope.variables.<name>` go through the same nearest-declaring-scope rule so reads and writes always meet one store (resolve-external-property-chain.ts:81-89). Variables are per action RUN: the root scope is created fresh by `_createScopeStack` for every start/end (action.ts:90-100), so variables do not survive from start operations to end operations or to the next run. A variable that was never set reads as `undefined` only if `variables` exists; otherwise `$scope.variables.x` throws `... 'variables' is undefined`? Precisely: with no scope declaring `variables`, fallback is the current scope, `scope['variables']` is undefined, then `.x` on undefined hits the intermediate-undefined error (get-property-chain-value.ts:62-66).

**Static or dynamic:** Variable existence/declaration order is statically analysable per action (straight-line + structured blocks). Compile to JS `let`/object-with-null-proto locals. Names come from config literals (static). Keep the null-prototype store if variable names can collide with Object.prototype members read via chains.

#### custom-function / get-import / systemName references (function references)

Operation `systemName` strings are resolved at configuration time by `importer.import(systemName)?.[systemName]` and must be a function that is not a controller/class/provider (configuration-resolver.ts:526-566, describeNonOperation 568+); unknown names throw with did-you-mean and the JSON path. `customFunction` (custom-function.ts:43-73) erases `systemName` first, then does a RUNTIME `eventbus.request('request-function', systemName)` through requestRegisteredEntry (request-registered-entry.ts:51-76; error 'customFunction: no function registered for systemName ...' / 'could not retrieve ...'), requires isFunction, and calls `func.apply(createScopeView(this), [operationData])`: the function gets the live flowing data object as arg and a Proxy over the scope as `this` whose reads fall through parents and whose writes/deletes go to the scope itself (80-105; only get/has traps are defined). The function's return value is ignored; only a returned thenable is awaited (65-69), then data resolves to `{...{}, ...operationData}`. The function may therefore mutate operationData arbitrarily, set `this.newIndex` (goto), `this.variables`, `this.loopIndex` ... `getImport` (get-import.ts:38-52) erases `systemName`, sets `importedInstance = requestRegisteredEntry(...)` (the same registry also serves operations, controllers, templates, json, as per the doc comment 18-27).

**Static or dynamic:** The name is static. The resolved function is only knowable at runtime because host code (EligiusResourceImporter({functions,...})) registers it, and the engine factory answers the eventbus request (engine-factory.ts:155-190). A compiler can emit `registry.get('name')` or an ES import ONLY when the host module is known at build time; otherwise the eventbus request must stay. Opaque functions force the 'bag object + real scope object' fallback.

#### template: / json: / config: placeholders (config-load-time syntax)

Run in two passes before anything else (configuration-resolver.ts:77-93, 766-935). Walk arrays and plain objects only (class instances/jQuery are skipped, 778-808). Pass 'import': a string value starting with `template:` is replaced by `importer.import(name)[name]` as-is (no copy), `json:` is replaced by a deepCopy of the same and marked in a WeakSet `imported` so its content is not scanned for placeholders (843-871). Unknown name -> `Unable to resolve placeholder '<ph>' at <jsonPath>: unknown name '<name>'.` (importPlaceholder 873-897 region). Pass 'config': `config:<chain>` resolved with resolvePropertyChain against the ROOT configuration (so it uses the same forbidden-segment/global-object guards and bracket/+suffix syntax), recursive follow-up of chained config: values, cycle detection error `Circular config: placeholder ...`, `undefined` result throws (resolveConfigPlaceholder 900-935; returned object is the shared reference, copied later by resolveOperation's deepCopy at line 559). Placeholders are detected by prefix on any string value anywhere in the configuration (including operationData), keys are not touched. Mutation: the passed `configuration` object is rewritten in place (configFragment[key] = ...).

**Static or dynamic:** Fully compile-time, provided the compiler has the same resources (templates/json/functions) as the runtime importer. Template/json values are host-provided and could be non-JSON (functions, DOM, class instances); the compiler can only inline JSON-serialisable values and must reference others via import.

#### Prototype-pollution and global-object guards: inventory

G1 forbidden chain segments (assert-safe-property-chain.ts:8-12,32-50): `__proto__`, `prototype`, `constructor`, checked on the part before '+' of each segment, run in resolveExternalPropertyChain on the raw split (resolve-external-property-chain.ts:43-47), again in getPropertyChainValue after bracket expansion (get-property-chain-value.ts:53), by setData on target segments (set-data.ts:80), and for config: chains. G2 global-object guard: any intermediate (index>0) or final value that is `globalThis` or has toString tag '[object Window]' makes the chain throw (get-property-chain-value.ts:68-70, 82-84, 100-107), which blocks e.g. `selectedElement.0.ownerDocument.defaultView`. G3 safe global names (globals.ts:38-44, used by setGlobals, addGlobalsToOperation, setGlobal) and null-prototype store with hasOwn reads (globals.ts:5,14). G4 setVariable name check + null-proto variables (set-variable.ts:41-45,53). G5 `assertNoProtoKeys` rejects an own `__proto__` key anywhere in configured operation data, raised at execution (action.ts:298-330). G6 own-`__proto__`-safe copying via Object.defineProperty in deepCopy and copyPlainObject (deep-copy.ts:66-74, resolve-property-values.ts:109-121). G7 `createElement` forbids 'script' and validates the tag name and attribute safety (create-element.ts:79-97) and `invokeObjectMethod` refuses native/code-executing functions, Function constructor, built-in/DOM/jQuery instances (invoke-object-method.ts:67-108, 125-239); these are operation-level security checks rather than data resolution. G8 `math` and `calc` use Object.hasOwn allowlists for the function / operator (math.ts:60-66, calc.ts:69-73).

**Static or dynamic:** G1 and G5 and the config-literal part of G3/G4: fully static for literal config, can become compile errors (or be dropped for checked literals). G2: dynamic, cannot be dropped for chains whose intermediate/final values are runtime objects (DOM nodes, jQuery, imported instances). G3/G4 stores: dynamic stores, keep null-prototype objects. G6: compile-time code must not emit an object literal with a quoted `__proto__` key (that sets the prototype); G7/G8: operation implementations, persist as long as the runtime operation functions are reused.

#### Where the interpretive cost in this layer actually is (evidence for H1)

Per execution of one operation the interpreter does: lookup + Object.assign merge (action.ts:181); a deepCopy of the full configured data if any value is an object (action.ts:352-360); for `when`, tokenize + parse + build the tree EVERY time with regex tests (parse-expression.ts:96-204, parse-operand.ts:55-73, no caching in when.ts:92); for each chain, `split`, `toLocaleLowerCase` x3 in isExternalProperty, `flatMap` + regex replace + `filter` + `assertSafePropertyChain` + a `reduce` with closures (get-property-chain-value.ts:46-80); `$globaldata` reads deep-copy the whole value; resolvePropertyValues deep-copies its input and walks it (resolve-property-values.ts:37-50); for `setData` builds a `targets` object including `getGlobals()` each time (set-data.ts:88-98). Operations run only at action start/end (engine calls `action.start()`/`end()` at range boundaries, e.g. eligius-engine.ts:947 and 1269; per-event for event actions, actionregistry-eventbus-listener.ts:50), never per tick. So the costs are real but amortised; the data-resolution layer gives a clear, measurable compile target (parse once, direct reads) without touching timeline scheduling.

**Static or dynamic:** Statically eliminable: expression parse, prefix/segment parsing, bracket expansion, safe-segment checks for literal paths, nested-config copying where not needed. Dynamic and irreducible: the property reads themselves, the global-object guard on runtime values, deep copies of runtime `$globaldata` values that actually escape.

### Compiler implications

- Precompute at compile time and delete from output: prefix detection (case-insensitive), `.`/bracket expansion, `+suffix` split, empty-segment drop, forbidden-segment rejection, all `when` tokenizing/parsing/syntax-error detection, and all `template:`/`json:`/`config:` placeholder resolution (given the same importer resources). These become literals, direct property-access expressions or compile errors.
- Emit exactly the opt-in resolution table: only the fields listed in the `Which operations resolve which fields` finding are lowered from `$`-strings to reads; every other string that looks like a chain MUST stay a literal string (e.g. setVariable.value, addClass.className, nested values inside setData values, array contents of forEach.collection, nested objects inside eventArgs). Encode this table as new generated metadata (a per-field `@resolves` / depth tag) so the compiler is driven by data, not a hand-copied list.
- Lower `when` expressions to a JS boolean expression: strict `===`/`!==`, raw `<,<=,>,>=`, parenthesise every comparison (grammar is non-chaining, one precedence level), `Boolean(L) && Boolean(R)` / `||` for and/or (keeps short-circuit and the boolean result), `!` for not, keywords true/false/null, JSON.stringify for quoted-string literals (raw inner text, no escapes), `Number()` result for numerics. Errors thrown by an unresolvable chain must stay lazy (only when the operand is evaluated, respecting short-circuit).
- Chain reads must keep their error contract: `<op>: property chain '<chain>' cannot be resolved: '<prefix part>' is undefined|null.` thrown only for null/undefined INTERMEDIATES; a missing leaf yields undefined; '' / 0 / false intermediates are indexable; inherited properties (`length`, methods) are readable. Provide one small runtime helper (e.g. `chain(root, ['a','b'], opName)`) or inline `a?.b`-style code that throws the same errors; embed the operation name statically (the interpreter derives it from scope.operations[currentIndex]) and attach `operationSystemName`/`operationIndex` to errors so EngineActionError keeps naming the failing operation (action.ts:265-277).
- Keep the global-object guard (G2) on any chain whose intermediates or leaf can be a runtime DOM/jQuery/imported object: a cheap `isGlobalObject` check on each non-primitive step. It can be elided only when the whole path is provably primitives/plain config-derived data (e.g. reading from a literal or a freshly built plain object).
- Preserve the three copy behaviours explicitly: `$globaldata` reads deepCopy the leaf (can be skipped only if the value is consumed read-only, e.g. in a comparison/truthiness test or used as a primitive); `$operationdata`/`$scope` reads return live references; `setGlobalData`/`setGlobals` store deep copies while `setData` onto `$globaldata.*` stores the resolved value by reference. Reuse the runtime `deepCopy` and the SAME `globals.ts` singleton so compiled code interoperates with customFunctions and the runtime engine, and keeps the clear-on-last-engine-destroyed lifecycle.
- Model operation data as local variables ONLY where the shape is fully static; the merge rule (config overwrites flowing keys) and each operation's erase set (verified per-operation table, `@erased` is advisory metadata and not authoritative) define liveness. Fall back to a real mutable bag object (and a real scope object with `newIndex`/`variables`/`parent`) after any customFunction, any `$operationdata` access whose key set is not statically known, any dynamic-key operation, or any init data from events/controllers (`eventArgs`). Event actions start with exactly `{eventArgs: [...args]}`; timeline/init actions start with `{}`; end operations never see start data.
- Nested config literals: emit fresh object/array literals per execution (and per loop, not per iteration, for forEach config), or hoist and `Object.freeze`/clone only when the consuming operation is known not to mutate or leak the value. The interpreter's guarantee is 'mutating nested config data never affects the next run'.
- Control flow: when/otherwise/endWhen map to if/else, forEach/endForEach/break/continue to `for` over `collection.slice()` with `break`/`continue`; compile `loopIndex`, `loopLength` (= length-1), `currentItem`, `variables` as lexical locals. Reject (compile error) unbalanced or crossing blocks and any write to reserved scope keys (`$scope.newIndex`, `loopIndex`, ... via setData) and any customFunction that relies on `this.newIndex`; the interpreter tolerates these but they cannot be structured JS. Offer a per-action fallback to the interpreter ('hybrid mode') for actions that use unsupported constructs.
- Await discipline: the interpreter keeps a run synchronous until an operation returns a thenable (action.ts:212-235). Only emit `await` after operations that can return promises (wait, loadJson, http*, startAction, endAction, animate*, plus dynamic checks after customFunction/invokeObjectMethod/addControllerToElement), not after every operation, otherwise same-tick ordering at seek/reconcile boundaries changes. Operation results of `undefined` must map to `{}`.
- Keep operations themselves as imported runtime functions (called with the `this` scope object they expect) as the first compiler milestone: this isolates the work to data-resolution/control-flow lowering and avoids re-implementing ~80 DOM operations. Inline only the hot data-plumbing operations (setVariable, setData, setOperationData, calc, math, when, forEach, selectElement's selector resolution, broadcastEvent argument resolution) once golden-output tests against the interpreter pass.

### Hazards

- Config-overwrites-flowing-data and in-place Object.assign mutation (action.ts:181-184): an operation's output key is silently replaced by a same-named config key of the next operation; mapping data to locals must apply the same last-writer rule including keys that an operation both reads and erases.
- A resolved `$operationdata.<ownKey>` sees the operation's OWN raw config merged in (e.g. `when` can read `$operationdata.expression`, `calc` with `left:'$operationdata.left'` resolves to the unresolved string). Compiled locals that skip the merge change behaviour.
- `loopLength` is lastIndex (length-1), not length (for-each.ts:49); the collection is snapshotted with slice() at loop start; `collection` is never erased and `currentItem` is deleted between iterations and after break/continue; `loopIndex` deleted by break lets `$scope.loopIndex` fall through to an OUTER loop by presence-based lookup (`head in scope`, resolve-external-property-chain.ts:107-113).
- Every `when` pushes a child scope whose `whenEvaluation` is its own; `setData '$scope.x'` with an empty path writes to that CHILD scope, but `$scope.variables.*` writes go to the root/declaring scope. A lexical translation must reproduce which writes are visible after endWhen.
- setData value vs setGlobalData copy semantics differ (reference vs deepCopy) and `$globaldata` reads copy while `$operationdata`/`$scope` reads alias. Dropping or adding a deepCopy changes behaviour when the value is later mutated by DOM ops, customFunctions, mapArray etc.
- setData root-target parsing strips the first character without verifying '$' (set-data.ts:70); `+suffix` with empty suffix silently drops the suffix; `a+b+c` keeps only 'b'; `$operationdata.` (empty path) returns the whole data object; empty segments are dropped; `[digits]` only is expanded. A re-implementation of the chain grammar that is 'cleaner' will diverge.
- Strict equality in `when`: `$x==null` is false for undefined; `'5'==5` is false; `<`/`>` use JS coercion; a quoted `'false'` or `'0'` is truthy; a missing value is falsy. JS `==` / `<` precedence levels differ from the grammar's single level (always parenthesise). `!` binds tighter than comparison.
- JSON.parse creates an own `__proto__` property, but an emitted object literal `{"__proto__": x}` sets the PROTOTYPE instead. Generated code must reject configs with `__proto__` keys at compile time (the interpreter throws at execution of that op, action.ts:318-322) or use computed keys. The same applies to emitted variable stores: keep Object.create(null).
- Error timing differs by design if the compiler fail-fasts: the interpreter surfaces unknown operands, bad syntax, forbidden segments and `Unrecognized target` only when that operation is reached, and `when` short-circuiting can skip an invalid chain entirely. Decide explicitly (compile error vs deferred throw) and test it.
- Math constant substitution runs AFTER chain resolution on runtime values: any string arg equal to an own non-function property of Math (E, PI, LN2, ...) becomes the constant (math.ts:79-94), even if it came from `$operationdata`. calc coerces both operands with unary plus (`+left`), so numeric strings work and non-numeric give NaN (calc.ts:75); the operator is validated AFTER erasure and with hasOwn.
- `removePropertiesFromOperationData` always erases `propertyNames` too and mutates the config array (remove-properties-from-operation-data.ts:22-24); `clearOperationData` without `properties` returns a fresh `{}` dropping everything (clear-operation-data.ts:299); `customFunction`'s return value is ignored and a promise result REPLACES the object identity (custom-function.ts:61-69).
- `$globaldata.x` read uses the live null-proto cache then deepCopies only the leaf; `getGlobals(name)` returns falsy values uncopied; custom host code and other engines on the page share the same store. Compiled code that keeps its own globals will desync from customFunctions and the runtime engine.
- `deepCopy` only copies plain objects, arrays, and the structuredClone set; class instances, jQuery objects, DOM nodes and functions are shared by reference. Treating all values as JSON in generated code would clone (or fail to clone) the wrong things.
- `start()`/`end()` data isolation: each run starts from `{}` or caller init data and end operations get no start data; variables are per-run (new root scope every start/end, action.ts:90-100). Emitting module-level `let` variables would leak state across runs/overlapping runs.
- Unbalanced or crossing when/forEach blocks are tolerated by the interpreter (skips to end of action, or a stray endWhen pops the root scope and crashes, action.ts:156,207); structured JS cannot express them. Break/continue inside nested whens unwinds via endWhen (pending jump) and that endWhen's cleanup is unobservable except that operations between are skipped.
- Synchronous-vs-async timing: awaiting every operation introduces a microtask turn between operations that the interpreter does not have (action.ts:197-238 loops synchronously until a thenable appears); the engine's seek/reconcile ordering and TimelineAction._sequence assumptions can break.

### Hypothesis verdicts

H1 (interpreter overhead small in practice; wins elsewhere): PARTLY SUPPORTED by this area. Operations run only at action boundaries (eligius-engine.ts:947, 1269; actionregistry-eventbus-listener.ts:50), never per tick. But the per-execution cost in the data layer is more wasteful than it needs to be and is purely interpretive: the `when` expression is tokenized and parsed on every execution with no cache (when.ts:92, parse-expression.ts:96-204), `$globaldata` reads deepCopy their leaf (resolve-external-property-chain.ts:51-54), chains are re-split, lower-cased and regex-expanded per read (get-property-chain-value.ts:46-80), and any nested config object triggers a full deepCopy on every execution (action.ts:352-360). Cheap interpreter-side fixes (cache parsed expressions on the resolved operation, pre-split chains at resolve time) would capture much of the speed win without a compiler, which supports H1's 'surest wins are elsewhere' framing. A compiler's data-layer benefit is therefore mostly startup, error quality and type checking, not tick time.

H2 (only the action/operation layer compiles away; engine runtime stays): STRONGLY SUPPORTED. The data layer cannot be self-contained: it depends on the global singleton store (globals.ts:5, cleared by engine-factory.ts:288-289), on an eventbus request for customFunction/getImport (custom-function.ts:48-53, request-registered-entry.ts:51-76, answered by engine-factory.ts:155-190), on `this.eventbus.request('request-engine-root')` (select-element.ts:70), and on a scope object that host functions may mutate (custom-function.ts:80-105). Output should be 'runtime library + generated action modules' that call the existing operation functions with a real scope object (at least initially).

H3 (runtime-dynamic values stay dynamic; paths compile to direct reads): SUPPORTED, with an important refinement. All chain sources are runtime (flowing data produced by earlier ops, `eventArgs`, globals, scope variables, loop item), but every PATH is static, parseable text. Only `forEach.collection`, `selectElement.selector`, `calc.operator`, `math.functionName` and `createElement.elementName` can ALSO be a chain whose VALUE selects behaviour (so the chosen branch/function is runtime); those must keep their runtime validation (hasOwn allowlists, tag-name regex, array check). Placeholders `template:`/`json:`/`config:` are the only values that are truly compile-time constants. The semantic details (non-owned reads of inherited properties, null-intermediate throws, copy vs reference per prefix, global-object guard) mean 'direct property access' must go through a thin helper or be generated with equivalent guards, not a plain `a.b.c`.

### Open questions

- Should compiled output support customFunction code that sets `this.newIndex`, `this.variables`, `this.loopIndex`, or depends on a Proxy scope view? That forces a real scope object and interpreter-compatible control flow. Decision needed: unsupported (compile error) vs a hybrid per-action interpreter fallback.
- Is the compiler's contract 'exactly reproduce interpreter semantics, including accepted-but-weird quirks' (setData first-char root parse, `+suffix`, empty-path chain, `$operationdata.<ownKey>` seeing raw config) or 'a documented stricter subset' that rejects them at compile time? The quirks above are probably untested edge cases; tests/ (src/test/unit/operation/helper/*) were NOT read in this pass to see which are intentionally pinned.
- Where should the per-field 'resolves chains' table (and depth: top-level vs deep) live? Today it exists only as code in ~10 operations; the generated metadata (tools/code-generator/metadata-generator.ts) has `required`/`erased`/`dependency` but nothing for resolution. A new doc tag plus metadata field seems necessary, otherwise the compiler hand-copies it.
- Do compiled actions need to appear as `IAction` instances (so TimelineAction._sequence, actionRegistry and `startAction` interop keep working), or can the engine run bare functions? `startAction`/`endAction` take `actionInstance` through operation data (start-action.ts:32-36), so interop with `requestAction` / getImport-provided actions is a design question (not examined here).
- How should template:/json: values that are not JSON-serialisable (functions, DOM) from `EligiusResourceImporter({templates,json,functions})` be handled at build time? Needs a decision on whether the compiler imports the host module or demands a JSON-only importer.
- Is deep-copying `$globaldata` reads observable by any shipped operation in a way that allows elision (consumers that only read)? A per-consumer 'does not retain or mutate' analysis would be needed; not performed.
- Event actions: `eventArgs` is `[...args]` shallow-copied (actionregistry-eventbus-listener.ts:50) but if `args` is not an array the raw value is passed; the controller path (controllers/helper/controller-actions.ts) supplies other init data shapes. The set of possible init-data shapes per action trigger was not enumerated here (probably another researcher's area).

## config-to-engine: Path from JSON configuration to a running engine, and the engine's runtime contract (resolver, factory, importer, entry points, build, API stability)

Pipeline: EngineFactory.createEngine(config, resolver?) (src/engine-factory.ts:232) imports the engine class by config.engine.systemName via the importer (:237), makes or reuses an Eventbus (:239-240), creates an ActionRegistryEventbusListener only if config.eventActions?.length (:296-298), runs ConfigurationResolver.process(config, listener) (:299-304) which returns [actionLookup, IResolvedEngineConfiguration], builds timeline providers from timelineProviderSettings (:306-312), registers request-instance/request-action/request-function responders (:317-325), the listener (:326-330) and a RequestVideoUriInterceptor (:331-336), builds LocaleManager from the RAW config (language, locales; :339-349), constructs `new EngineClass(resolvedConfig, eventbus, timelineProviders, localeManager, timelineProvidersByUri, localesReady, engineOptions)` (:352-360), then connects three adapters (:363-377). The caller then drives engine.init()/start().

The resolver (src/configuration/configuration-resolver.ts) does five things: (1) mutates the INPUT config in place to substitute `template:`/`json:` (pass 'import') then `config:` (pass 'config') placeholders (:79-95, 775-865; this is a side effect on the caller's object); (2) validates structure and produces JSON-path errors; (3) resolves each operation systemName to a function via importer.import(name)[name] and rejects non-operations (controllers, providers, custom functions, classes; :526-591); (4) wraps operations into Action/EndableAction/TimelineAction instances bound to the eventbus (:735-764, 707-733, 473-492); (5) builds the name->action lookup (actions + eventActions only) and registers event actions on the listener only after the whole config is accepted (:153-168). Everything else in IResolvedEngineConfiguration is deep-copied data.

Key finding for a compiler: the only function/class-valued parts of IResolvedEngineConfiguration are IAction instances (initActions, actions, timelines[].timelineActions) and, inside them, IResolvedOperation.instance. The engine never touches operations or operationData directly; it only calls action.start()/end() and reads action.active/duration/id/name. So the exact seam where generated code plugs in is the IAction/IEndableAction/ITimelineAction interface (src/action/types.ts:1-18), plus the lookup Record<string,IAction> served by 'request-action'. A generated module can construct an IResolvedEngineConfiguration directly and EngineFactory.createEngine already accepts a custom IConfigurationResolver (src/types.ts:520-525, factory :299-304) as a supported injection point, but the factory still needs a raw IEngineConfiguration for engine.systemName, eventActions (to decide whether a listener exists), language and locales, and still uses the importer for the engine class, position sources, container providers, playlists and the request-instance / request-function responders (controllers, customFunction, getImport). So 'skip the resolver' is feasible with no API change; 'skip the importer' is not without factory changes.

### Findings

#### IResolvedEngineConfiguration shape: data vs functions/classes

src/configuration/types.ts:102-115. #### What the engine requires from an action object (the seam)

Interfaces src/action/types.ts:1-18: IAction {id, name, startOperations: IResolvedOperation[], start(initData?): Promise<TOperationData>}; IEndableAction adds endOperations and end(initData?); ITimelineAction adds `get active(): boolean` and `duration: IStrictDuration`. #### Action lookup (startAction / requestAction / controllers) membership and registration

actionsLookup = createActionsLookup([...resolvedConfig.actions, ...eventActions]) (configuration-resolver.ts:153-160, 450-468). #### Event actions

Event action = plain `Action` (start only; no endOperations) built in resolveEventActions (configuration-resolver.ts:473-492), id left as '' (Action.id default, action.ts:12), `eventName`/`eventTopic` kept beside it, registered via ActionRegistryEventbusListener.registerAction(action, eventName, eventTopic) with key `eventName:topic` when topic non-empty (actionregistry-eventbus-listener.ts:11-23). **Static or dynamic:** Registration table (eventName, topic, action) is fully static; operation data `eventArgs` is runtime.

#### Timeline action duration validation and normalisation

resolveDuration (configuration-resolver.ts:679-705): duration must be an object; start finite number >= 0; end optional; undefined or -1 => end normalised to -1 (open end); non-finite or non-number end throws; end < start throws; start==end allowed (zero-length action, scheduled with order 2 after its own start, eligius-engine.ts:1394). Error text includes JSON path `timelines[i].timelineActions[j].duration[.start|.end]`. The TimelineAction gets `{start, end}` as IStrictDuration and `action.id = id` after construction (:724-732). The engine itself sorts events stably by position, then order (ends 0 < starts 1; zero-length ends 2), starts keep config order, ends at the same position sorted highest start first (eligius-engine.ts:1402-1412). **Static or dynamic:** Entirely static; a compiler can validate once and emit {start,end} literals plus (optionally) a pre-sorted schedule.

#### Resolver side effects and mutation vs copy

process() MUTATES its argument: resolvePlaceholder assigns configFragment[key] = template/json/config value into the caller's object (configuration-resolver.ts:827-853). `json:` values are deep-copied from the importer (:846) and tagged in a WeakSet so they are not walked (:851-853), `template:` strings are assigned directly, `config:` values are assigned by reference to the target value (no copy, :827-831,937) after following chains (cycle detection :910-915; undefined target is an error :928-932). Passes: 'import' for the entire tree first, then 'config' (:79-95) so config: always sees the substituted value. Only plain objects and arrays are walked (isPlainObject cross-realm safe; class instances/jQuery objects from the TS API are kept, :772-775,799). Prefix literals: `template:` (9 chars), `json:` (5), `config:` (7) (:834,843,917). Resolved operationData is `deepCopy(operationConfig.operationData) ?? {}` (:559). Resolved timelineProviderSettings, cssFiles, availableLanguages, timelineFlow deep-copied; engine info shallow-copied (:111). Note: the resolver does NOT copy `locales`; factory reads raw config.locales, so placeholders inside `locales` ARE also substituted since they are inside the same walked config object (locales is a property of the root).

**Static or dynamic:** All placeholders are statically resolvable if the compiler is given template and json sources; `getImport`/`customFunction` names are runtime lookups through request-function.

#### Operation resolution rules (what makes a systemName valid)

resolveOperation (configuration-resolver.ts:526-562): importer.import(systemName)?.[systemName]; importer throw -> rewrapped as Unknown operation with cause (:534-541); non-function -> Unknown operation (:543-545); then describeNonOperation rejects names listed as controller/provider/function by the importer's optional getControllerNames/getProviderNames/getFunctionNames (when NOT in getOperationNames) and anything whose Function.prototype.toString starts with `class` (:564-595). **Static or dynamic:** Static for built-ins and for custom operations the compiler is told about (needs the same name->module mapping the importer holds); the host-registered set is otherwise only known at runtime.

#### Timeline provider construction: what is data and what is class

timelineProviderSettings are plain config consumed by the factory, never by the engine (grep). #### Operation execution semantics the generated code must reproduce (from the Action runner, which is the thing being replaced)

Action.executeOperation (action.ts:140-246): (1) Operation data object is MUTATED, not copied, across operations: `Object.assign(operationData, configuredData)` merges the configured operationData INTO the previous operation's output object, configured keys overwriting same-named previous keys (:181-184). The previous op's returned object is the same identity the next op receives. (2) configuredData: undefined -> shared frozen {} (:279,348-350); data with a nested object/array value -> deepCopy on EVERY execution (:352-361), else the configured object itself (safe because Object.assign copies top-level keys only). Also assertNoProtoKeys walks the configured data once per object (WeakSet) and throws `<systemName>: operation data must not contain a '__proto__' key (found at '<path>')` (:298-330). (3) forEach iterations reuse the first iteration's copy (_loopOperationData WeakMap keyed by the loop scope, :175-177,194). (4) Return value: `result ?? {}` for sync results (:237); if the result is a promise (isPromise), execution continues in .then with the resolved value (which is not defaulted here but the next executeOperation call defaults undefined to {} via `previousOperationData ?? {}`, :145,149); synchronous operations run in a while loop without microtask hops, so a fully synchronous action completes its Promise executor synchronously (TimelineAction relies on this: timeline-action.ts:92-96). (5) Control flow: scope.newIndex jump consumed at the top of each iteration (:157-160); end-of-list check `index >= operations.length` resolves with the CURRENT operationData (:164-167); `when` pushes a scope BEFORE calling the operation and forEach pushes one (non-iteration) with `owner` = the operation record and calls with the pushed scope as `this` (:186-195); endWhen pops after the call, endForEach pops only if it did not set newIndex (loop continues) (:202-208). Detection is by the literal systemName strings from when.ts/for-each.ts (imports at action.ts:4,7). (6) Error annotation: any throw/rejection becomes reject(withOperationContext(err, op, index)): non-Error values are wrapped (`new Error(String(e), {cause})`), and operationSystemName/operationIndex are set ONLY if not already set (innermost wins, :265-277). Index is the index within the list being executed, not a global one. (7) Failures are not logged by Action; the caller reports (documented :36-41). (8) start(undefined) behaves as start({}) in the first op. (9) `endable.end()` with an empty endOperations list resolves immediately with `initOperationData ?? {}` WITHOUT creating a scope (endable-action.ts:390-392) while start() with empty startOperations still resolves via the runner with {}. (10) TimelineAction semantics layered on top (timeline-action.ts:54-135): start is a no-op resolving {} if already active, end is a no-op resolving {} if not active; flags flip synchronously; a start/end issued while operations of an earlier run are still pending is queued (_waiting) and executed once the earlier run SETTLES (including on failure, via onSettled) so start and end operations of one action never interleave; an end without end operations still goes through _sequence so ordering holds.

**Static or dynamic:** These semantics are static properties of the runner. A compiler can emit straight-line code that preserves them (shared mutable data object, top-level merge of config literals, `?? {}`, sync/async split, error annotation) or can prove, per operation, that a copy is unnecessary. Whether an operation returns a promise is dynamic unless metadata says so (the metadata has no async flag; see open questions).

#### Error behaviour a compiled build must keep or consciously change

Resolver errors (fail-fast, JSON paths) become COMPILE-time errors in the compiler (so they must be ported, ideally reusing the same messages) but a runtime-loaded config still hits them. Runtime error shapes visible to host code: EngineActionError message `Error in action <phase> '<name>' at operation '<systemName>' (index <i>): <cause message>` with fields actionName, actionId, phase, operationSystemName, operationIndex, cause (eligius-engine.ts:55-90); the operationIndex is the index in the start or end operations array (so compiled code must either keep the same operation list indices or consciously change; hence 'readable stack traces' win vs. exact message parity); the error is emitted on engine 'error' and forwarded as 'engine-error' on the eventbus; with no non-forwarding subscriber the engine console.errors (:1516-1526, 1523). Init action failures reject engine.init() (init actions are awaited in _initializeTimelineProvider, :946-954) rather than going through 'error'. ### Compiler implications

- Plug in at the IAction/IEndableAction/ITimelineAction duck-typed interface (src/action/types.ts). The engine needs only: name, id, start(), end(), active (synchronous flip), duration {start, end} with end -1 meaning open. Everything else in Action (scope stack, operation loop) is internal and replaceable.
- Generated output should be a factory function (e.g. createCompiledConfig(eventbus)) returning {actionLookup, resolvedConfiguration}, because actions are stateful per engine (TimelineAction._active/_running/_waiting) and capture the eventbus at construction; it can be passed as an IConfigurationResolver to the existing EngineFactory.createEngine (engine-factory.ts:299-304) with a thin stub IEngineConfiguration (engine.systemName, language, locales, and a non-empty eventActions marker if the resolver registers event actions on the listener). No breaking API change is required for this path.
- Keep runtime classes TimelineAction's sequencing (queueing of start/end behind running operations) and the Action runner's error annotation (innermost operationSystemName/operationIndex wins) as shared runtime pieces; generated code should supply per-action run functions and let a compiled wrapper class (a subclass of TimelineAction/EndableAction overriding _runOperations, or a new class implementing the same interface) provide active/_sequence. Reimplementing TimelineAction semantics per action in generated code would duplicate subtle behaviour (timeline-action.ts:54-135).
- Compile-time (static) work: placeholder substitution (template:, json:, config:), duration validation/normalisation (end -1), duplicate action name check, operation name validation, provider-settings validation and merge (timeline-provider-overrides.ts is pure and reusable), sorting of the schedule (optional; engine sorts at init anyway), event-action registration table, startAction/requestAction targets with literal names (direct references instead of request-action), customFunction/getImport/getControllerInstance with literal systemName (direct imports).
- Runtime-only: DOM/selector resolution, request-engine-root, eventbus requests for controllers/functions with computed names, event args, globals, locale loading, position sources and providers (classes need the DOM), the eventbus itself and the adapters. Per H2 the compiled output is 'engine runtime + generated action modules'.
- The factory still needs an importer for the engine class, position sources, container providers, playlists, and the three request-* responders. Provide (additive) a minimal importer builder that imports only the used operations, controllers and providers so tree-shaking works; EligiusResourceImporter's `import * as ops` + Object.keys defeats tree-shaking (eligius-resource-importer.ts:3,87,135).
- A DOM-free, Node-runnable compiler entry must not import the resolver, the importer, action modules or any operation implementation (jquery@4 throws without a window; src/metadata.ts:1-21 explains). It should depend on eligius/metadata + types + pure helpers, and follow the existing pattern: its own tsdown build entry (tsdown.config.ts:165-173), an exports key and typesVersions entry (package.json:188-212), a domFreeDtsBanner, and a check-dist-types scenario and a node-environment spec that mocks jquery and lottie-web to throw. The generated code, by contrast, imports from the main 'eligius' entry (operations are exported by name, index.ts:20) so there is one module instance and one global store.
- Do not ship the compiled-runtime helpers as a separate bundle that re-bundles operation or global-store modules: module-level singletons (globals cache globals.ts, loadJson cache, liveEngineCount in engine-factory.ts:62) would be duplicated and break shared state and cleanup. Either re-export them from the main entry or externalise 'eligius' in the new build.
- Preserve error semantics: EngineActionError fields and message depend on err.operationSystemName/operationIndex. Generated code must attach these (same index within its list) or the engine's error message degrades; this is the main place where 'readable stack traces' (H1 win) conflicts with message parity, so decide explicitly.
- Preserve the observable ordering of init: init actions run sequentially and are awaited one by one, each added to the started set only after its start resolves, and are ended in reverse order at destroy (eligius-engine.ts:946-954,1189-1191).

### Hazards

- The resolver mutates its INPUT configuration (placeholder substitution in place, configuration-resolver.ts:827-853). A compiler that reuses or mirrors this logic must not assume purity, and a runtime path that processes the same config twice sees already-substituted values; `json:` is deep-copied from the importer but `template:` and `config:` results are assigned by reference.
- Placeholder order: all template:/json: before any config: (two passes, :79-95); json values are marked in a WeakSet and never walked for nested placeholders (:851-853, 783); only plain objects/arrays are walked, so TS-API class instances are untouched. `config:` follows chains and detects cycles; an undefined target throws.
- Actions in the lookup are only `actions` + `eventActions`; initActions and timelineActions are not addressable by startAction/requestAction/controllers (configuration-resolver.ts:153-160). Do not generate name references to timeline or init actions. Names are unique across actions and eventActions only (duplicates among timeline action names are allowed).
- Event actions are plain `Action` (id '' and no end), and their initial operation data is `{eventArgs: [...args]}` freshly created per event per action; sharing one object would leak state between actions (actionregistry-eventbus-listener.ts:46-51). Timeline/init actions get `undefined` initial data (engine calls start() with no args), so the first operation receives a fresh `{}`.
- Operation data is one mutable object threaded through the chain: configured data is Object.assign'ed INTO the previous result (configured keys win), not the other way round; configured objects with nested values are deep-copied on every execution (but only once per forEach loop), and top-level-only configured data is shared by reference and relies on top-level copy semantics. Operations that delete or reassign properties (erased) mutate the shared object, so aliasing assumptions (e.g. hoisting configured literals as module constants) can corrupt later runs if a nested value is handed out un-copied.
- `result ?? {}` for sync results but the async continuation passes the awaited value as-is (possibly undefined; defaulted to {} on the next executeOperation call). A compiled version that awaits every operation would add microtask hops and break the TimelineAction invariant that fully synchronous actions finish within the same call stack (timeline-action.ts:92-96). It must only await when an operation actually returns a promise.
- Control-flow detection in the runner is by literal systemName ('when', 'forEach', 'endWhen', 'endForEach' constants imported by action.ts:4,7) and when/otherwise/forEach compute their jumps at runtime from scope.operations with findMatchingOperationIndex (for-each.ts:116,126; otherwise.ts:21,33). A compiler that emits native if/for must also remove the need for scope.operations and newIndex, but `this` passed to operations (customFunction scope view, assertSafePropertyChain reading operations[currentIndex].systemName) still expects a scope object with operations/currentIndex/eventbus. A custom operation registered with override named like a control-flow op is treated as control flow too.
- The scope object a nested operation sees is a pushed child scope for when/forEach, with currentIndex/eventbus/operations delegated to the parent through accessors (action.ts:110-131); loopIndex, currentItem, variables, whenEvaluation, owner, newIndex live on specific scopes and `$scope.` chains read through the parent chain (custom-function.ts:228-254). Emitting plain JS locals for these breaks operations that read this.* chains.
- The runtime import graph of the resolver is not DOM-free (action.ts imports operation modules), so importing the resolver for compile-time validation in Node can load jquery and crash. Use metadata and pure helpers instead (verify with ts_dependency_tree on action.ts, for-each.ts, when.ts; UNVERIFIED here).
- EngineFactory reads TWO configs: the resolved one via the resolver and the raw one for engine.systemName, eventActions?.length, language and locales (engine-factory.ts:236, 296, 339-349). A compiled path that only returns a resolved configuration silently loses locales and the event-action listener unless the raw stub carries them.
- Timeline providers are keyed by timeline type AND by uri; representativeTimeline picks the first timeline of a type that does not override the type settings, shared intrinsic-container sources (video) are shared by key `type:sortedJSON(config)`. These decisions are order-dependent and duration-dependent (position source gets `duration: timeline.duration` of the representative timeline), so a compiler that precomputes provider plans must replicate them exactly or leave provider creation to the factory.
- The importer's class detection for controllers/operations uses Function.prototype.toString regex /^class[\s{]/ (eligius-resource-importer.ts:311-316, configuration-resolver.ts:593-595): transpiled/minified output that lowers classes to functions will be mis-classified, and compiled/minified operation functions are fine, but custom controllers compiled down to ES5 will fail registration.
- Ordering semantics of timeline dispatch live in the ENGINE, not in actions: ends before starts at the same position, zero-length actions (start==end) order 2, ends highest-start-first, stable start order, pending-start gate (eligius-engine.ts:1400-1412, 1602-1709). The compiler must NOT re-implement scheduling; it should only provide the actions and their duration.
- Per-engine isolation: compiled action instances capture the eventbus and (for TimelineAction) hold state; a module-level singleton would be shared across two createEngine calls on the same module or across hot reloads. The global data store and loadJson cache are module-wide and cleared only when the last live engine is destroyed (engine-factory.ts:62,285-290).
- resolveDuration treats `end: -1` and missing end identically (open), and the engine reads end < 0 as Infinity without mutating the action (eligius-engine.ts:233-236). A compiled `duration` must follow the same normalisation or the engine's schedule differs (an open-ended action would get a finite end event).
- tsdown alias plugin omits @adapters and @locale though tsconfig.json defines them (tsdown.config.ts:87-107 vs tsconfig.json:3-14); a new module in a new alias folder (e.g. src/compiler) must update tsconfig, vitest and tsdown aliases together, and the metadata/config-api DOM-free guarantee must be re-verified for any new entry.

## tooling-and-prior-art: Existing code generation tooling, metadata, and prior art (Eligius tools/, generated metadata, fluent API, Eligian DSL)

Eligius ships three ts-morph based metadata generators in src/tools/code-generator/ (operations: metadata-generator.ts, controllers: ctrls-metadata-generator.ts, events: events-metadata-generator.ts), a ts-json-schema-generator based schema generator (src/tools/schema-tools/generate-schemas.ts, 735 lines, also emits jsonschema/operations/*.json), a README generator and a dist type-checker. The generated operation metadata is pure DATA: one function per operation returning IOperationMetadata<TData> {description, category, dependentProperties?, properties?, outputProperties?} (src/operation/metadata/types.ts:34-40). Properties carry only a ParameterType string (33 editor-hint names from src/operation/metadata/parameter-types.ts:13-47), optional itemType for arrays, literal-union value lists, required, erased, description. It is exposed DOM-free via src/metadata.ts (entry eligius/metadata) and the fluent ConfigurationFactory is DOM-free via src/configuration-api.ts. 79 metadata files exist for 79 operations (82 files in the dir incl. index/types/parameter-types).

Metadata is sufficient for a SHALLOW static dataflow check (does a dependency exist upstream, which keys are erased, which keys are declared as output), and Eligian already does exactly that (F:\projects\eligius\eligian\packages\language\src\dataflow\operation-dataflow.ts, compiler/transformers/erased-parameters.ts, compiler/operations/metadata-converter.ts + generated registry.generated.ts with 79 ops). It is NOT sufficient for a sound type-check of an operation chain or for codegen of the data flow: (a) outputProperties lists only properties tagged @output (37 of 79 metadata files have it); the true output type lives only in the TOperation<TIn, TOut> second generic (e.g. Omit<..> & ..), which the generator ignores (metadata-generator.ts:70-88 reads only typeArgs[0]); (b) dynamic-shape operations (setOperationData, customFunction, invokeObjectMethod, startAction/endAction/requestAction, loadJson, addGlobalsToOperation, clearOperationData, removePropertiesFromOperationData, setVariable/setData) mutate the bag in ways metadata cannot express (keys come from config values); (c) metadata does not say WHICH parameters are run through property-chain resolution ($operationdata./$globaldata./$scope.) and how (resolveExternalPropertyChain vs resolvePropertyValues vs internalResolve, used by 15 of 79 operation files); (d) it does not say if an op is async, mutates in place vs returns a new object, uses the scope, or touches the DOM; (e) ParameterType names are editor hints, several map to one JSON type (parameter-type-schema.ts:9-45); (f) dependency entries have no 'consumed/erased' flag. So a compiler needs either richer metadata (new JSDoc tags) or hand-written per-operation codegen templates, with metadata used only for validation.

Eligian (F:\projects\eligius\eligian, version dependency eligius 4.0.0, package.json:34) is a Langium DSL compiler. Its pipeline (packages/language/src/compiler/pipeline.ts): parse -> transformAST -> typeCheck -> optimize (dead-code only, optimizer.ts) -> emitJSON (emitter.ts is just adding $schema). Its IR IS an IEngineConfiguration (eligius-ir.ts:50-55) plus a source map. It imports the DOM-free eligius/metadata entry (metadata-converter.ts:8) to generate its operation registry, already does constant folding of DSL constants (constant-folder.ts), dataflow contract inference, and works around the shared-bag semantics (erased-parameters.ts saves/restores action parameters that an op would erase). Its CLI bundler (cli/src/bundler/runtime-bundler.ts:150-260) already emits a standalone JS bundle that is "imports of used operations + JSON.stringify(CONFIG) + BundledResourceImporter + EngineFactory", i.e. ENGINE + CONFIG (selective operation imports = a primitive form of tree-shaking, but no codegen of actions). No spec in either repo discusses compiling actions to JS; Eligius specs/ mention only TypeScript compile-time typing (specs/003-eventbus-typing). Best fit: add a back end that consumes the same IEngineConfiguration IR (Eligian -> IEngineConfiguration -> compiled JS) so that hand-written JSON and Eligian share one compiler; Eligian-direct emission would lose JSON parity and duplicate semantics.

### Findings

#### Operation metadata shape and what it knows

IOperationMetadata<T> = {category, description, dependentProperties?: (keyof T)[], properties?, outputProperties?} (src/operation/metadata/types.ts:34-40). Property = TParameterTypes string | {type, defaultValue?, required?, erased?, description?} | {type:'ParameterType:array', itemType} (types.ts:10-32). type may be a list of {value, default?} literal unions. Example addClass: dependentProperties ['selectedElement'], properties {className:{type:'ParameterType:className',required:true,erased:true}} (src/operation/metadata/add-class.ts). selectElement: properties selector (erased, required), useSelectedElementAsRoot (erased), outputProperties selectedElement:'ParameterType:object' (src/operation/metadata/select-element.ts). Control-flow ops forEach/when have properties only (forEach.collection type 'ParameterType:array|ParameterType:string' required, NOT erased; when.expression erased). 19 ops have no 'properties' block at all (break-for-each, continue-for-each, end-for-each, end-when, otherwise, clear-element, remove-element, toggle-element, set-focus, get-*, add-controller-to-element ...). Only 37 of 79 have outputProperties.

**Static or dynamic:** Static: metadata is generated plain data, loadable in Node without DOM via eligius/metadata (src/metadata.ts:1-19).

#### How the metadata is derived (ts-morph)

metadata-generator.ts loads ./src/operation/*.ts with ts-morph (lines 23-31), takes the first exported variable statement, reads the FIRST type argument of the TOperation<...> type reference by AST text (lines 53-88: deliberately text, not the checker, so generics resolve to the written interface name), finds the interface/type alias in the same file, and emits one file per op. Tags: @dependency -> dependentProperties (getDependentPropertyNames, line ~190), @output -> outputProperties, no tag -> properties; per-property @type=ParameterType:x overrides inference (getTypeFromTag in shared.ts), @required, @erased booleans. @category is read from the exported variable's JSDoc; description = JSDoc comment text. Type inference (property-type.ts): strip null/undefined; boolean-literal union -> boolean; literal union -> value list; other union -> '|' joined ParameterTypes; Record/unknown/any -> object; X[] -> array+itemType; function types -> function; unknown names throw via assertParameterType against PARAMETER_TYPES (shared.ts:~205). The SECOND generic (output type) and the function body are never inspected. Operations lacking a data interface get TOperationData (Record<string,any>) (metadata-generator.ts:90-110, 129-140).

**Static or dynamic:** Static (build time). Gap: output shape (Omit<...> etc.) exists only in TS types, not in metadata.

#### Fluent ConfigurationFactory as programmatic input/IR builder

**Static or dynamic:** Static build-time builder; produces the IEngineConfiguration a compiler consumes.

#### Runtime semantics the metadata cannot express: operation-data bag

Action.executeOperation (src/action/action.ts:129-270) keeps ONE mutable operationData object. Per operation: configuredData = copyConfiguredOperationData(opInfo.operationData) (deep copy only when configured data contains a nested object, otherwise the frozen/shared object is reused; throws on own __proto__ key at any depth, action.ts:298-362); mergedOperationData = Object.assign(operationData, configuredData) i.e. CONFIGURED VALUES OVERWRITE same-named earlier outputs and the previous object is MUTATED in place; the op is called with this = scope; the return value (or {} if undefined/null, action.ts:237) becomes the next bag; a returned promise is awaited and its result continues the chain (async chain via recursion on promise). Errors are annotated with operationSystemName and operationIndex (withOperationContext action.ts:~266-285) and rejected; execution stops. Sync ops run in a loop, no stack growth.

**Static or dynamic:** Dynamic by default, but the merge/overwrite order is fully static per op instance except for runtime-supplied initial data (event args, startAction merges).

#### Control flow is index-jumping over the flat operation list

when pushes a child scope (action.ts:187-189), forEach pushes a child scope with owner and caches configuredData in _loopOperationData so later iterations reuse the first iteration's merged data (action.ts:176-186, 190-196); forEach finds its matching endForEach by counting nesting at first iteration (for-each.ts findEndForEachIndex uses findMatchingOperationIndex) and sets scope.loopIndex/loopLength (= length-1)/loopStartIndex/loopEndIndex/currentItem; collection is snapshotted (slice) in a WeakMap (for-each.ts); empty or null collection sets newIndex = loopEndIndex; a non-array resolved collection throws 'forEach: Expected resolved collection property to be array type'. endWhen/endForEach pop the scope (action.ts:222-228) unless endForEach set newIndex (looping back). Unmatched whens/loops fall off to operations.length (end of list) - so malformed pairing is silently tolerated at runtime and a compiler must decide to reject or replicate. Scope variables (setVariable) live on the scope that declares `variables`; $scope reads walk parent scopes (resolve-external-property-chain.ts getScopeChainValue/findDeclaringScope).

**Static or dynamic:** Pairing and nesting are statically known from the flat list (except when startAction/requestAction target actions looked up by name at runtime). Loop collection and when-values are runtime.

#### Property-chain resolution is per-operation and implicit

Strings of the form $operationdata.a.b / $globaldata.x / $scope.loopIndex (case-insensitive prefix) in an operation's data are resolved only if that operation calls one of the resolve helpers (15 operation files use resolveExternalPropertyChain/resolvePropertyValues/internalResolve/resolvePropertyChain; 64 do not). E.g. selectElement resolves only `selector` (select-element.ts), forEach resolves only `collection`, setOperationData resolves `properties` recursively through plain objects/arrays (resolve-property-values.ts: deep-copies the separate properties object, copy-on-write for nested). $globaldata chains return a deepCopy of the global (jQuery/DOM/functions/class instances by reference); assertSafePropertyChain guards __proto__/prototype/constructor and operation name is embedded in errors via getCurrentOperationName(scope). This knowledge (which param resolves) exists only in code, not metadata.

**Static or dynamic:** Whether a given string is a chain is static (prefix check); the resolved value is runtime. Which parameter an op resolves must be hand-encoded or added as new metadata.

#### Mutation vs copy, op by op examples

selectElement mutates the incoming bag (assigns selector, removeProperties erases selector/useSelectedElementAsRoot, sets selectedElement) and returns it (select-element.ts). setOperationData builds a NEW object via spread (set-operation-data.ts); override:true returns only resolved properties and drops the whole existing bag. addGlobalsToOperation uses Object.assign on the bag and copies plain globals (add-globals-to-operation.ts). startAction destructures caller data, runs the callee with mergeOperationData(callerData, actionOperationData), and afterwards continues with {...callerOperationData, actionInstance} - callee changes never flow back (start-action.ts) and the op always returns a Promise (so even sync-looking chains become async at that point). loadJson is async. Control ops (forEach, when) return the bag unchanged and communicate through the scope. Because ops mutate the shared bag, aliasing between configured objects and results is possible only through nested objects (hence the conditional deepCopy of configured data).

**Static or dynamic:** Per-operation static facts; a compiler can encode each op's behavior in a template.

#### Operation typing facts relevant to type-checking a chain

TOperation<T,RT=T> = (this: IOperationScope, data:T) => Promise<RT>|RT with TOperationData = Record<string, any> (src/operation/types.ts). ExtractReturnedOperationData<T> (types.ts bottom) can recover the output type at TS level, so the real output type IS available to a ts-morph/tsc based tool even though the metadata generator ignores it. Examples: selectElement output Omit<ISelectElementOperationData,'selector'|'useSelectedElementAsRoot'>; getImport output Omit<RequireKeys<..., 'importedInstance'>,'systemName'> (get-import.ts:35-38); loadJson Omit<..,'url'|'cache'>. So a TS-typed generated chain (each step as a typed function over an evolving object type) is feasible by emitting calls like `const d2 = await selectElement.call(scope, {...d1, selector})` and letting tsc check them, but the bag is Record<string,any>-typed at the config boundary and events/args/globals are untyped.

**Static or dynamic:** Compile-time type derivation is possible with ts-morph; value-level facts (event args, globals) are runtime.

#### Where a compiler fits relative to Eligian

Recommended: Eligian -> IEngineConfiguration (already its IR, eligius-ir.ts:50) -> new Eligius 'config -> JS modules' compiler (lives in the eligius repo, consumes the same JSON schema and metadata, DOM-free entry). Reasons: (1) single semantic implementation next to the operations whose behavior it must replicate; (2) hand-written JSON gets compiled too; (3) Eligian already treats IEngineConfiguration as the interchange format and emits source maps keyed by action/operation ids (SourceMap, eligius-ir.ts:70-80) that can be extended to map generated JS back to DSL. A hybrid: the compiler accepts optional structured hints (e.g. Eligian could keep a structured control-flow tree in IR) later. The erased-parameters workaround in Eligian exists only because of the shared bag; a compiled backend using locals removes that class of workaround, but must produce identical observable behavior for configs relying on the bag (collisions).

#### Prior art: Angular Ivy, Svelte, Solid, XState typegen, Lottie

Angular Ivy (locality, tree-shakable instructions): compiled output is calls to small runtime instruction functions (ɵɵ…) rather than a bundled interpreter, which makes the runtime tree-shakable and templates incrementally compilable per component; lesson: compile to calls into a small stable runtime ABI, not to a re-implementation of the runtime, and keep a JIT/interpreter fallback for dynamic cases (Angular kept JIT for dev/tests). Svelte/Solid: template -> imperative DOM code with fine-grained updates; the win was less runtime and no vdom diff, but the real gains came from eliminating per-update interpretation and from static analysis of what can change; lesson here: in Eligius the hot path is not updates but action boundaries, so the analogue is removing the bag/resolver machinery per op (H1 caveat: benefits are modest unless profiling shows op-chain cost matters). XState typegen: generated types/metadata from machine definitions give IDE-checked event/state names while the interpreter remains runtime; lesson: type generation without semantic changes is cheap and often captures most of the DX benefit; typegen later was dropped in favor of TS-inference-based typing (XState v5 setup()) - warning about maintaining a parallel generator/toolchain whose output drifts from the library. Lottie-to-code tools (e.g. Lottie -> native/Lottie-compose, lottie-web renderers vs generated vector code): converting JSON animation to code gives smaller/faster output but loses features (expressions, dynamic properties) and requires a fidelity test corpus comparing frames; lesson: build a conformance harness that runs every fixture config through both interpreter and compiled path and diffs observable effects (DOM, eventbus events, errors). General: ship interpreter and compiler behind one semantic spec and differential tests; support a fallback per action ('uncompilable -> keep config-interpreted') so the compiler can be incremental. (These are conceptual summaries from general knowledge, not verified against sources in this session.)

**Static or dynamic:** N/A (prior art).

### Compiler implications

- MUST reproduce, per operation instance, the exact order: copy-or-share configured data (with __proto__ key assertion at compile time instead of runtime) -> Object.assign(bag, configured) (configured overwrites same-named bag keys, bag object is the same identity) -> call op with scope -> next bag = result ?? {} -> await only when the op returns a promise. A compiler may replace the bag by locals only where it can prove no op reads keys it did not statically know about (customFunction, invokeObjectMethod, setOperationData override, clearOperationData, addGlobalsToOperation, startAction/requestAction and anything touching `this.operations`), otherwise it must keep an object bag for those segments.
- Compiled output can usually still CALL the existing operation functions (they are plain functions typed TOperation) with a synthesized scope; the first and safest step is to eliminate the interpreter loop, ConfigurationResolver lookup and runtime pairing scans (findMatchingOperationIndex) and unroll when/forEach into native if/for. Inlining operation bodies (second step) needs per-operation templates, because metadata lacks output shape, chain-resolved params, async-ness and mutation info.
- Metadata alone suffices for: operation-name validation, required-parameter presence, parameter-type warnings (coarse), dependency-presence checks (dependentProperties vs earlier outputProperties/erased), category-based decisions. It does not suffice for sound type-checking of dynamic ops or typed output of ops with no @output tags. Extend the generator (reuse ts-morph code: read TOperation's 2nd generic via ExtractReturnedOperationData, add new JSDoc tags such as @resolves-chain, @async, @pure, @mutates) rather than hand-maintain a table; keep metadata.ts DOM-free.
- Reuse: eligius/metadata and eligius/configuration-api (DOM-free) for the compiler front end, generate-schemas JSON schema for input validation, Eligian's IEngineConfiguration IR and SourceMap for diagnostics. The compiler should live in the eligius repo (new entry e.g. eligius/compiler, DOM-free, Node-only) and Eligian should call it on its IR.
- Emit a 'compiled action' as an object implementing the same IAction shape (start/end returning Promise, plus id/name) so EligiusEngine, timeline dispatch, event actions, init actions and startAction(actionInstance) keep working with a mixed config (compiled + interpreted actions). Per-action fallback to the interpreter should be possible. Ensure error annotation (operationSystemName, operationIndex) is reproduced on the thrown Error since the engine's error event reads them.
- Differential test harness: run every existing fixture/integration config through interpreter and compiled path and compare DOM, eventbus broadcasts and errors; reuse specs/TESTING-GUIDE.md patterns and applyOperation/createDefaultScope.
- Dynamic names (getImport, customFunction, requestAction, startAction targets, controller names) resolve via eventbus/importer at runtime; compiled output either keeps those requests or statically binds when the name is a literal and the resource is registered at compile time (needs the compile-time importer map).

### Hazards

- Object.assign(bag, configured) mutates the previous bag AND lets configured keys clobber earlier outputs of the same name; converting the bag to locals silently changes behaviour for configs that rely on overwrite, on erased keys becoming undefined, or on nested object identity sharing.
- Returned undefined/null becomes {} (action.ts:237) - an op returning nothing resets the bag (not 'keep previous'). forEach/when return the same bag; set-operation-data with override drops the whole bag.
- Configured data is shared (not copied) when it has no nested object/array values (action.ts copyConfiguredOperationData), but deep-copied if any nested object exists; ops that mutate nested configured data would otherwise corrupt repeat runs. In a compiled action constants must be re-created or deep-cloned per execution when ops can mutate them.
- forEach: first-iteration configured data is cached in _loopOperationData and reused for later iterations (action.ts:176-196), and loopLength is length-1 (for-each.ts); the collection is resolved once and sliced; empty collection jumps to endForEach index; continue/break use scope.newIndex and clearLoopCollection. Nested loops/whens each push a scope; endWhen/endForEach pop it; unmatched ends/starts do not error at runtime (fall to end of list).
- when/otherwise/endWhen set scope.whenEvaluation and skip operations by newIndex; the when expression language (parse-expression.ts) has && || ! parentheses, strict ==/!=, short-circuit, operands including $scope.* and $globaldata.*, and throws on unknown operands. Compiled JS must keep truthiness rules ('false' and '0' strings are truthy) and short-circuit semantics, and must not emit eval.
- $scope chain resolution walks parent scopes to the one that declares the head property (variables live on the root scope, not the child scope of a loop/when); setVariable and setData use the same rule.
- Case-insensitive prefix match of $operationdata/$globaldata/$scope; chains are guarded (assertSafePropertyChain, prototype-pollution + global-object guards) and errors embed the operation name; generated direct property access (a.b.c) must keep the same guards for config-derived chains and the same error text if tests assert it.
- $globaldata reads return deepCopy (references kept for jQuery/DOM/functions/class instances) - emitting direct reads from the global store would break the copy semantics.
- Async: any promise-returning op (loadJson, wait, http*, startAction, endAction, requestAction, animate*) switches the rest of the chain to promise continuation; synchronous chains stay synchronous (no stack growth). Generated code that is async-all-the-way changes timing (microtask yields) versus the interpreter, which may reorder DOM updates relative to timeline ticks.
- Rejections: Action rejects with an Error annotated by withOperationContext; non-Error throws are wrapped (new Error(String(e),{cause})). Scope stack is per execution (start()/end() create it; _initializeScopeStack is deprecated).
- metadata 'erased' means the op deletes the key from the bag AFTER reading it; 'dependency' means must exist upstream; neither says whether an op also mutates other keys. Eligian's erased-parameters.ts shows the practical consequence (action parameter erased by selectElement).
- Metadata description strings are included in generated files and contain JSDoc; shared.escapeTemplateLiteral is needed for any generated template literal.
- Generated metadata dirs are gitignored and absent on a fresh clone - a compiler that imports eligius/metadata needs npm run metadata/build first; the Eligian registry (registry.generated.ts) is a second generated snapshot that can drift from eligius version (it embeds 'Generated:' timestamp and op count 79).

### Hypothesis verdicts

H1 (interpreter overhead small; wins elsewhere): Not contradicted by this area. Evidence that per-op overhead is concentrated in cheap-ish but non-trivial work per op: Object.assign merge, assertNoProtoKeys (memoized in a WeakSet, action.ts:~299), conditional deep copy, per-op property-chain checks, scope push/pop, WeakMap loop bookkeeping (action.ts:129-270, for-each.ts). Those matter for loops over large collections and for async chains, not for tick processing. Non-performance wins that the tooling directly supports: tree-shaking (the Eligian bundler already imports only used ops, runtime-bundler.ts; dynamic importer.import(systemName) is the thing defeating it), skipping ConfigurationResolver (configuration-resolver.ts), readable stack traces (error annotation currently by index only), type-checked output (ts-morph typing of TOperation output generics, ExtractReturnedOperationData). No benchmarks exist in the repo for this; I did not measure. H2 (only action/operation layer compiles away): Supported. Position sources/providers are resolved by name via the importer from timelineProviderSettings (configuration-resolver.ts:~215-430), controllers are attached through addControllerToElement at runtime, and Eligian's bundler still emits EngineFactory + config, so 'engine runtime + generated action modules' is the natural shape. H3 (runtime-dynamic values stay dynamic): Supported. Property chains ($operationdata/$globaldata/$scope), forEach collections, when operands and event args all resolve at runtime; metadata has no value-level information, only ParameterType hints. Statically foldable subset: literal configured data, constant expressions (Eligian already folds DSL constants in constant-folder.ts), pairing of control-flow ops, used-operation set.

### Open questions

- Do any shipped configs rely on collisions/overwrite semantics of the shared bag or on unbalanced when/forEach (silently tolerated at runtime)? A corpus scan of examples and tests is needed to decide strict-vs-faithful compilation.
- Should the compiler consume the resolved IResolvedEngineConfiguration (after ConfigurationResolver, needs importer + DOM-free operation loading) or raw IEngineConfiguration JSON (needs a compile-time name->operation map, which the DOM-free metadata entry cannot provide because operations import jQuery)? Probably raw config + generated import statements.
- How to expose output shape and chain-resolving params to the compiler: new JSDoc tags and generator changes versus a hand-written per-op codegen table; which ops (customFunction, invokeObjectMethod, setOperationData, clearOperationData, removePropertiesFromOperationData, addGlobalsToOperation, setData, setVariable, startAction, endAction, requestAction) must be treated as 'opaque bag' barriers.
- Is there profiling data showing the op-chain interpreter is a measurable cost (H1)? No benchmark in repo; recommend measuring a loop-heavy config before committing to inlining.
- Eligian pins eligius 4.0.0 and its bundler still has video.js leftovers (spec 006 critique); who owns keeping the Eligian registry in sync and where the shared 'IEngineConfiguration with structured control-flow hints' contract would live?
- I did not read src/tools/doc-tools, schema-tools/html-tag-names.ts, video-options-rule.ts, check-dist-types.ts, ctrls/events generators in full, nor specs/*/spec.md beyond keyword greps (no hits for compilation/AOT/performance/DSL in Eligius specs apart from the 006 critique files). ## benchmark: interpreter overhead measured

Ran: true. Cleanup verified: true.

### Method

Existing benchmark: only src/test/unit/performance/timeline-benchmarks.spec.ts (timeline init, lookup and engine switching; nothing about operation execution), and package.json has no bench script. I wrote one temporary spec, src/test/unit/aot-overhead.tmp.spec.ts, using the real Action class (src/action/action.ts:12), the real operation functions, a real Eventbus answering 'request-engine-root' with a jsdom jQuery root (5 .item spans), and the real ConfigurationResolver. The createMockAction and createMockEventbus fixtures were not used because they are vi.fn mocks that would skew timing; the mock action has no operations loop anyway. The action has 13 operations: selectElement, addClass, setData, setOperationData with a $operationdata chain, when/removeClass/otherwise/addClass/endWhen, then forEach over a 20-item literal array with setOperationData ($scope.currentItem), setData ($operationdata.last = $operationdata.current) and endForEach. The hand-written equivalent is a plain async function with the same jQuery calls (find, addClass, removeClass), an if/else and a for loop, and the same operation-data object spreads. Each variant ran 200 warm-up iterations, then 3000 measured iterations, run twice, keeping the faster run, timed with performance.now() and reported as microseconds per run. Scenarios: full action, without forEach (9 ops), without when (8 ops). Attribution used synchronous micro-benchmarks (20000 iterations, 1000 warm-up), identity-operation shells, loop variants with only one body operation type, and a per-operation wrapper timing the real interpreter over 1000 runs. The resolver was measured on 10 actions of 13 ops each, 500 iterations. The spec ran under vitest 5.0.5 (vmThreads, jsdom) on the user's Windows machine. Three full runs of the final spec; the numbers below come from the last run, and earlier runs agreed within about 10 percent.

### Where the time goes

Where the interpretive overhead goes (all timings are my own measurements from the temporary spec).

1. Per-iteration loop work in the forEach, not per-action overhead. The loop body ran 20 times and used about 80 to 90 percent of the full action's time (583 us interpreted vs 60 us for the same action without forEach). The wrapper timing of the real interpreter (777 us total with timers on) put 236 us in the loop's setOperationData (20 calls, about 12 us each), 142 us in the loop's setData (about 7 us each), 18 us in forEach and 13 us in endForEach. The 9 non-loop operations together took about 76 us.

2. resolvePropertyValues, deepCopy and property-chain safety work, mostly through setOperationData. The standalone cost of resolvePropertyValues on 2 properties is 5.7 to 7.4 us (src/operation/helper/resolve-property-values.ts:34). It deepCopies the properties object each call (src/operation/helper/resolve-property-values.ts:35), and deepCopy of a small object is about 0.9 to 1.1 us. The loop variants isolate this: an empty forEach body costs 26 us for 20 iterations; a setOperationData with a literal value 115 us (about 4.4 us per call); the same with '$scope.currentItem' 217 us (about 9.5 us per call). So a chain lookup via resolveExternalPropertyChain costs about 5 us extra: split on '.', assertSafePropertyChain, getCurrentOperationName, scope-chain walk (src/operation/helper/resolve-external-property-chain.ts:19 to 46). A setData-only loop body costs 198 us (about 8.6 us per call), versus 1.6 to 2.0 us for setData called standalone with a plain scope. In the real interpreter it is slower, and I did not isolate why; the pushed loop scope is a getter/setter proxy (src/action/action.ts:99 to 120), and the action also deep-copies the configured operation data (the nested 'properties' object) on every run of the operation (src/action/action.ts:288 to 306). That per-iteration copy is the likely contributor, but I did not isolate it.

3. Scope bookkeeping and loop control are cheap by comparison. A forEach with an empty body is 26 us for 20 iterations (about 1.3 us per iteration, covering forEach, endForEach and the executeOperation while-loop). Two identity operations in the loop body add about 19 us (about 1 us per iteration, covering the Object.assign merge and WeakMap lookups). Thirteen identity operations with no flow control cost 3 to 4 us in total (about 0.25 us per op). The shell test (flow-control ops real, all others identity) was 51 to 68 us for the whole 13-op action.

4. The when block costs about 80 us. parseExpression plus evaluateExpression costs 6.4 to 6.7 us per call, because the expression is re-parsed on every run (src/operation/when.ts:19 to 20; no caching), and when itself is about 8 us standalone, roughly 17 us measured inside the interpreter. Removing the when block took about 80 us off the 583 us, which is consistent with when plus otherwise/endWhen plus their branches (about 40 us in the wrapper timing).

5. The promise chain is negligible. An empty Action.start() costs 0.43 to 0.56 us, a bare async function 0.17 to 0.25 us. All operations here are synchronous, so executeOperation never crosses a promise boundary (src/action/action.ts:229 to 246) and there is no promise chaining cost.

6. The real DOM work is shared and substantial. root.find('.item') is about 5.5 to 5.8 us and addClass about 1.0 to 1.2 us. These appear in both variants, so they set the compiled floor (about 13 to 20 us per run). The eventbus request for the engine root is only 0.05 us.

7. Resolver startup: about 1.1 ms one-time for 130 ops (about 8.5 us per op), compared with 8.4 us to construct the same objects directly.

### Conclusion

H1 (interpreter overhead may be small) is only partly supported. In absolute terms it is small: about 0.5 ms for a heavy 13-op action with a 20-iteration loop, about 60 us for a loop-free 9-op action. That is well inside a 16 ms frame, and the 100 ms default tick interval means actions would have to fire in bulk to matter. In relative terms it is large: 3x for a loop-free action, 27 to 37x for the 20-item loop action. The cost is mostly in loops with property-chain resolution (setOperationData and setData), each costing 5 to 12 us per call, and the interpreter's own bookkeeping is cheap (about 0.25 us per op for scope, merge and promise). So the compiler's payoff is workload-dependent. For ordinary presentations (a handful of operations per action, loops of under 10 items) it saves tens of microseconds per action. It would help for loop-heavy or large-collection actions, or if actions fire hundreds per second. The one-time resolver cost (about 1.1 ms for 130 ops) is also minor, but it scales with config size and could matter for startup of very large presentations. Compiler design would need to account for safety checks (proto-key, property-chain assertions) that are part of the interpreter's measured cost, since a compiler that drops them is not equivalent. The other benefits named in H1 (tree-shaking, readable stack traces, type-checked output) are not measured here. Recommendation: do not justify the compiler on runtime speed alone, but speed gains on loop-heavy actions are real and large in relative terms.

### Caveats

- Single machine, single jsdom/vmThreads run environment, no isolation from other processes; numbers vary about 10 percent run to run (the faster of two passes was kept), and absolute values will differ in a real browser where jQuery find and addClass run on a real DOM.
- The hand-written variant skips the safety logic the interpreter performs (proto-key checks, assertSafePropertyChain, the sanitised scope getters), so the ratio overstates what an equivalent safe compiler could achieve. I did not write a compiled variant that keeps those checks.
- The hand-written variant uses plain jQuery calls and object spreads, not the operation functions called directly; I did not measure a middle variant (direct operation calls with a static scope), so the split between operation-function cost and Action loop cost is inferred from the micro-benchmarks and the wrapper timing.
- The wrapper timing adds performance.now() overhead per operation (total 777 us vs 583 us unwrapped), so per-operation figures are inflated by roughly 30 percent; the loop-variant measurements (no wrapper) are cleaner.
- Tick cost (range checks in the engine's action dispatch) was not measured, only action execution; whether operations run at action boundaries rather than every tick is from reading the code, not from a benchmark here.
- The mock eventbus and mock action fixtures were deliberately not used because vi.fn wrappers would distort timing; a real Eventbus was used instead.
- The forEach collection is a literal array of 20 numbers; larger collections or collections read from $globaldata (which deepCopies) would shift the ratio.
- The Action does not retain a few intermediate keys the same way as the hand-written version (the interpreter leaves 'collection' in the returned data), so I checked that every key of the hand-written result exists in the interpreted result rather than strict equality.
- First resolver attempt failed because actions require an endOperations array; I fixed the config and the run succeeded, so the three-attempt budget was not exhausted.
